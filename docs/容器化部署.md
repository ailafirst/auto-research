# 容器化部署

> 除模型服务外全部组件在容器里，`deployment/start-all.ps1` 一条命令拉起。
> 本文讲**改动前需要知道理由的那几条**；照着跑的步骤见 [根 README](../README.md) A 节。
> 没用过 Docker 的话先看第一节，够读懂后面就行。

## 一、先补概念

### 为什么要容器

这个项目要同时跑起来 7 个东西：Web 服务器、API、多个任务 worker、MySQL、Redis、Qdrant。改造前它们是**手工装在机器上**的：Nginx 解压到 `C:\nginx-1.28.0`、配置文件里写死项目的绝对路径、Redis 靠一个单独的 compose 文件、worker 靠开多个终端各跑一条命令。

问题不在于麻烦，而在于**换一台机器就要重来一遍，而且没人说得清「一遍」到底包含哪些步骤**。装了什么版本、改了哪个配置、哪个服务要先起——这些知识散在人的记忆里。

容器把「一个程序 + 它依赖的整个环境（操作系统的库、Python 解释器、装好的依赖包、配置文件）」打包成一个**能整体启停、换台机器行为一致**的单元。上面那些知识因此变成了仓库里可读、可 diff、可回滚的文件。

### 几个词

| 词 | 是什么 | 本项目里对应 |
|---|---|---|
| **镜像 image** | 只读的「安装包」，含程序和它要的全部环境。构建一次可反复使用 | `deepresearch-app`（api/worker 共用，723MB）、`deepresearch-web`（Nginx + 前端静态文件，48.6MB） |
| **容器 container** | 由镜像**启动起来的实例**。镜像与容器 ≈ 安装盘与装好的系统；同一个镜像可以起多个容器 | 2 个 worker 容器就是同一个 `deepresearch-app` 镜像起了两份 |
| **Dockerfile** | 构建镜像的脚本（装什么、拷什么、启动时跑什么命令） | `deployment/docker/Dockerfile` |
| **Compose** | 用一个 YAML 描述「这一堆容器分别是什么、谁依赖谁、端口怎么开」，然后一条命令全起 | `deployment/docker/compose.yaml` |
| **数据卷 volume** | 由 Docker 管理的独立存储。**容器删了它还在** | `mysql-data` / `qdrant-data` 等 5 个；删容器不会丢任务记录和向量 |
| **端口映射** | 容器内的端口默认外面碰不到，要显式映射到宿主机。写法是 `宿主机端口:容器端口` | `"80:80"`（对外）、`"127.0.0.1:3307:3306"`（只对本机） |

两条容易踩的网络规则，后面反复用到：

- **容器之间用「服务名」当主机名互访**，不用 IP。所以配置里写的是 `redis://redis:6379`、`mysql:3306` —— `redis`、`mysql` 是 compose 里的服务名，只在容器网络内部解析得了，在宿主机上敲这个地址是不通的。
- **容器要访问宿主机上的程序，用 `host.docker.internal`**，不能用 `127.0.0.1`（在容器里 `127.0.0.1` 指的是容器自己）。

> Windows 上的 Docker Desktop 实际是在一个 WSL2 的 Linux 虚拟机里跑容器。所以「宿主机」和容器之间隔着一层网络，也因此让容器用上显卡要额外配置——这是模型服务留在宿主机的原因之一。

### 日常三条命令

```powershell
docker compose -f deployment/docker/compose.yaml ps         # 谁在跑、健康不健康
docker compose -f deployment/docker/compose.yaml logs api   # 看某个服务的日志（排查第一站）
docker compose -f deployment/docker/compose.yaml down -v    # 停掉并删除数据卷（慎用，数据全没）
```

启停用 `deployment/start-all.ps1` / `stop-all.ps1` 即可，一般不用直接敲 compose。

## 二、形态

```
宿主机   model-server :8100  ←──┐  容器经 host.docker.internal 访问
                               │
容器     nginx :80 ──→ api ────┤
                   ↘  worker × N
                        ↘ mysql（任务 SoR） / redis（队列·缓存·限流） / qdrant（向量）
```

- 对外只有 `:80`。mysql / redis / qdrant 各有一个**仅绑 `127.0.0.1`** 的调试映射（3307 / 6380 / 6334）——不写这个前缀时 Docker 默认绑 `0.0.0.0`，等于把基础设施暴露到局域网。api 无宿主机映射，只能经 nginx 访问。
- 模型服务留在宿主机：要 GPU、要 7.1GB 权重、冷启动 100 秒的有状态单例，和可随时重建的 api/worker 不是一类进程。
- **它必须监听 `0.0.0.0`**：容器经 `host.docker.internal` 走的是宿主网卡地址而非回环，听 `127.0.0.1` 时容器侧连不上。`-ModelServerHost` 默认已是 `0.0.0.0`。

## 三、关键设计

**1. 应用镜像刻意不含 torch。** api/worker 全程 HTTP 调模型服务，不 `import torch`。镜像 723MB，装上 torch 要 +5236MB；更要紧的是 `rag_service` 那条「模型服务不可达就回退本地加载」的降级路径——装了 torch 它会**真的能跑**，于是每个 worker 各自默默装一份 bge-m3 把内存吃干净；不装则是明确的 `ImportError`，故障从静默变可见。依赖据此拆成 `requirements.txt`（核心，进镜像）/`-model.txt`（+torch，宿主机）/`-dev.txt`。

**2. 凭据。** 四个口令在 `deployment/docker/.env`（不入库，首次启动生成随机值），compose 里一律 `${VAR:?...}` 而非 `${VAR:-默认值}`：缺任何一个直接启动失败，不悄悄退回弱口令。

> **规则：凡是把 DSN 交给日志或响应体的地方，必须先过 `app/core/config.py` 的 `mask_dsn()`。** 口令写在 URL 里，而 `/health` 经 Nginx 公网可达。

`/health` 的 `detail`（内部主机名、端口、库用户名、版本、异常原文）同理默认不返回，需带 `X-Health-Token`。没按来源 IP 判内外网——公网入口是 frp 隧道，frpc 在宿主机回连 `127.0.0.1:80`，Nginx 看到的 `$remote_addr` 和本机访问一样，IP 层面分不开。

MySQL 口令只在数据卷**首次初始化**时生效（卷已存在时改配置不会改变库里的实际口令），轮换必须走 `ALTER USER`，见 README A7。

**3. 健康检查查「能不能用」不是「在不在」。** compose 可以给每个容器配一条健康检查命令，别的容器靠它判断依赖是否就绪。MySQL 原先用 `mysqladmin ping`——它**认证失败时也退出 0**，只能证明端口通，已换成实跑 `SELECT 1`。api 的检查则只判「进程活着且能响应」：`/health` 恒返回 200，健康度在 body 的 `status` 里；否则 Redis 抖一下就会把一个完全可以降级运行的 API 判成 unhealthy 并重启。

**4. 开发态→部署态的数据差异。**

| 项 | 要点 |
|---|---|
| SQLite → MySQL | `tasks.data` 存完整任务 JSON。**MySQL 的 `TEXT` 只有 64KB**，故用 `Text().with_variant(LONGTEXT, "mysql")` |
| Qdrant 内存 → 远程 | 由 `QDRANT_MODE` 显式切换，不是「配了 URL 就用远程」；不可达自动回退内存，实际模式看 `/health` |
| upsert 分批 | 一个任务 2000+ chunk 会超请求体上限，而**失败会被当成「Qdrant 不可用」静默跳过整个证据构建**（任务照常完成、报告零引用）。故 256 一批 |
| 向量 TTL | `VECTOR_TTL_DAYS=7`，worker 内 arq cron 范围删除；配套建 `task_id`/`created_at` 的 payload 索引 |

## 四、踩过的坑

| 现象 | 原因 / 解法 |
|------|-----------|
| Redis 口令成了字面量 `${REDIS_PASSWORD}` | compose 的 `command:` 是 exec 形式，容器里没有 shell 去展开变量。这里要用单 `$` 让 compose 在编排侧插值；`healthcheck` 的 `CMD-SHELL` 才轮到容器内 shell，用 `$$` |
| 报告零引用但全程无报错 | qdrant-client 与 server 版本不兼容（要求 major 相同、minor 差 ≤1）。`upsert` 失败且异常消息为空。升 client 时 compose 里的镜像版本要跟着升 |
| 宿主机上 httpx 连 `127.0.0.1:8100` 返 502 | httpx 默认 `trust_env=True`，在 Windows 上**还读注册表里的系统代理**，连回环也被塞进代理。解法 `trust_env=False` |
| `.ps1` 报离奇语法错 | PS 5.1 按 ANSI 读 `.ps1`，中文注释按 GBK 解码会吞换行。脚本须存成 **UTF-8 with BOM** |
| 生成的 `.env` 第一个键名解析不出 | `Set-Content -Encoding UTF8` 在 5.1 下写 BOM。改用 `[IO.File]::WriteAllLines(..., UTF8Encoding $false)` |
| 脚本输出一重定向就报「构建失败」 | compose 进度走 stderr，`Stop` 模式下被包成 ErrorRecord 抛出（退出码其实是 0）。调用前后临时置 `Continue`，成败以 `$LASTEXITCODE` 为准 |
| `/health` 中文变 `arq å·²è¿æ¥` | FastAPI 的 Content-Type 不带 charset，`Invoke-RestMethod` 按 ISO-8859-1 解。改用 `Invoke-WebRequest` 自己按 UTF-8 解字节 |

## 五、文件

```
deployment/
├── start-all.ps1                   # 唯一入口（旧的三层脚本已删）
├── stop-all.ps1                    # 默认只停不删，数据卷保留
├── remove-legacy-c-drive.ps1       # 清理 C 盘旧 Nginx / frp，一次性
└── docker/
    ├── compose.yaml  Dockerfile  nginx.conf  .env.example
    └── migrate_sqlite_to_mysql.py  # SQLite → MySQL，幂等

app/services/health_service.py      # 五项依赖探测，启动校验与 /health 共用
app/core/config.py                  # mask_dsn / qdrant_mode / vector_ttl_days / health_detail_token
```

`start-all.ps1` 最后一步会逐项校验依赖，任何一项不通即报错退出：**降级是运行期的容错能力，不是一次成功部署的可接受终态。**
