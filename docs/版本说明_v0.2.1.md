# 版本说明 v0.2.1 — 多轮增量补证 · 全局目标锚定 · 信源与报告抗幻觉 · 全节点降本

> 主线：在 v0.2.0 服务化基础上，围绕**报告质量**与**成本/延迟**两条线做深度优化——多轮补充从"整图重跑"改成"局部增量补证 + 复用 + 置信停止"；零新字段的全局目标锚定防跑偏；工程化的学术源双路提升信源权威度；CoVe（方案丙）在放开"通用知识兜底"的同时压住幻觉；并以实验驱动**全节点关思维链 + 冗余 max_tokens** 大幅降本提速。全部**不引入新依赖**，延续"降级安全"风格。

## 本版改动一览

| 模块 | 改动 | 实测 / 依据 |
|------|------|------|
| 多轮补充（②）| 整图重跑 → 增量补证：只重做核查未通过子问题、复用通过项、Citation Registry 追加式跨轮稳定、失败集空即停 | 见重点二 |
| 全局目标（③）| 零新字段，复用 `query` + `research_goal`，接线 planner / report_writer / fact_checker | 见重点三 |

## 重点一：报告自然行文改造（首要）

### 1.1 问题：报告死板固定，是模块拼接而非分析文章

现状产出读起来像"把各子问题的答案裱起来"，而不是一篇有论点、有起承转合的分析文章。根因在代码里是**结构性**的，不是提示词措辞不到位：

| 根因 | 位置 | 说明 |
|------|------|------|
| 骨架被硬编码 | `app/prompts/report_writer.md` §格式适配 | `deep` 明写"分析（**各子问题独立成节**）"——报告结构 1:1 镜像子问题拆解 |
| 输入即预切块 | `nodes.py:1099` `sub_answers_text` | 喂给 LLM 的是 `### 问题 / 置信度 / 回答 / 引用` 分块串联，天然诱导"逐块成节" |
| 低温度固化 | `nodes.py:1155` `temperature=0.3` | 偏确定性，进一步强化模板化行文 |

结论：只要"报告结构 = 子问题列表"这个映射不打破，换措辞也只是把模块换个说法拼。**必须让结构从「发现」里长出来，而不是从「问题拆解」里长出来。**

### 1.2 方案：两阶段写作（先谋篇，再行文）

把 `report_writer_node` 从"一次成文"改为两阶段，中间加一个**结构规划**pass：

```
sub_answers（各子问题结论 + 证据 + 引用）
  │
  ├─ 阶段 A：结构规划（新增 LLM pass，短、低温 0.3）
  │    产出「论点驱动的大纲」：中心论点 + 3–5 个主题小节
  │    —— 主题可跨子问题聚合，允许合并/拆分/重排，不与子问题一一对应
  │    —— 输出 JSON：{ thesis, sections:[{heading, covers:[子问题id], angle}] }
  │
  └─ 阶段 B：行文（改造现有 pass，中温 0.5–0.6）
       按大纲写连贯散文，把 sub_answers 当**证据池**而非章节
       跨小节引用具体证据 [C01]…，保留 Citation Registry 约束
```

**关键改动点：**

1. **提示词重写** `report_writer.md`：
   - 删去 `deep` 的"各子问题独立成节"，改为"围绕中心论点组织，跨子问题综合证据，禁止逐题罗列"。
   - `report_type` 从"固定章节骨架"降级为**篇幅/语气/侧重**指引（summary 短平快、comparison 必含对比表、deep 充分展开），仅保留最小结构底线（标题 / 摘要 / 结论 / 参考来源），正文结构交给阶段 A 的大纲。
2. **输入重构** `nodes.py:1099-1105`：`sub_answers` 不再以 `###` 分块标题喂入，改为"带 id 的证据条目"，措辞上定位为"素材"，弱化其"章节感"。
3. **两阶段实现**：阶段 A 复用 `_ANALYST_RESPONSE_FORMAT` 同款 JSON-schema 结构化输出拿大纲；阶段 B 沿用 `_llm_with_short_retry`。
4. **温度**：阶段 A 低温（结构稳定），阶段 B 提到 0.5–0.6（行文自然）。

**约束不变（防跑飞）**：
- "所有结论必须基于子问题分析结果，不引入分析外信息" 保留。
- Citation Registry（`C01/C02…`）仍是唯一引用真源，阶段 B 只允许用注册表内 id。
- 报告生成前 fact_checker 已跑过，证据边界已定。

### 1.3 落地档位（可分步上）

| 档位 | 改动量 | 效果 | 代价 |
|------|--------|------|------|
| **A. 仅改提示词**（先做，验证方向）| 只改 `report_writer.md` + 输入措辞 | 松绑骨架，行文自由度立增 | 无额外 LLM 调用；结构仍靠单 pass 自发 |
| **B. 两阶段**（推荐目标）| A + `report_writer_node` 加结构 pass | 论点驱动、跨子问题综合，最接近"分析文章" | +1 次短 LLM 调用（末节点、每任务一次，延迟可控）|

**建议**：先上档位 A 用现有 benchmark 任务肉眼验证"是否更像文章"，方向确认后再上档位 B。两档都对现有引用/核查链路零破坏。

### 1.4 验收

- 主观：3–5 个 benchmark 任务人工对比改造前后，看是否"围绕论点行文、跨子问题综合、无逐题罗列感"。
- 客观护栏：引用有效性（无注册表外 id）、事实核查通过率、报告长度分布不劣化。
- A/B 口径沿用仓库既有纪律：同批任务、只改报告层一个变量。

## 重点二：多轮增量补证（只补需要的，正确的复用）

### 2.1 问题：补充轮次把整图重跑，已通过的子问题白算一遍

`research_runner.run_research()` 的多轮 `while` 循环（`research_runner.py:200-233`）在每个补充轮次：

- 携带 `sub_questions / research_plan / research_strategy`，但把 `search_results / crawled_documents / evaluated_sources` 清空（`:217-228`）；
- 调 `_run_round()` **重跑整张图**（`:229`）——planner 虽在 round>1 跳过重规划，但 **analyst 会把所有子问题重分析一遍、fact_checker 把所有子问题重核查一遍**。

而补充轮次的 `follow_up_queries` 只针对**上一轮核查未通过**的子问题。于是：

- **速度浪费**：已通过的子问题被无谓地重跑 analyst + fact_checker（分析/核查是最贵的 LLM 环节）。
- **质量隐患**：已通过的答案被重新生成，非确定性下可能**回退**（本来对的变错）。

### 2.2 方案：补充轮次只处理"失败子问题"，通过的原样复用

已有现成的机制可借：`_revise_citations()`（`research_runner.py:157-185`）已经证明"只重跑 analyst→fact_checker→report_writer 子集"完全可行。把补充轮次改造成同款**部分重跑**：

```
上一轮 fact_check_result.issues（按 sub_question_id + 严重类型）
  → 定位失败子问题集合 F（follow_up_queries 本就服务于 F）
  → 补充轮次只对 F：
       retriever → extractor → evaluator → evidence_builder   （仅 F 的 follow_up 查询，产出增量证据）
       analyst(only_ids=F) → fact_checker(only_ids=F)
  → 合并：sub_answers = 复用(通过的) + 修订(F 的)
          citation_registry = 追加式（老 C01… 稳定，新证据续 Cnn）
  → report_writer 末尾对合并后的全集跑一次
```

**关键改动点：**

1. **节点加子集过滤**：`analyst_node` / `fact_checker_node` 增加可选 `only_sub_question_ids` 参数（analyst 本就按子问题循环 `nodes.py:764`，加一层过滤即可；不传时全量，向后兼容）。
2. **证据增量累积**：`retriever_node` 已按 `sub_question_id` 标记结果，补充轮次只喂 F 的 follow_up 查询即可天然 scope。Citation Registry 改**追加式**——通过子问题的 `C0x` 保持不变，新证据分配新 id，保证 report_writer 看到并集且引用稳定。
3. **控制流改造**：仿 `_revise_citations`，新增 `_run_supplementary_round(failed_ids, follow_up, carried_state)`，直接调节点函数（不走整图 astream），复用已通过子问题的 `sub_answers` 与其引用。
4. **进度语义**：前端轮次时间线（`RoundTimeline`）已在；补充轮次的进度可标注"仅补充 N 个子问题"，让"只补需要的"对用户可见（延续 v0.2.0 过程透明）。

### 2.3 收益与风险

| 维度 | 说明 |
|------|------|
| **速度** | 若 N 个子问题中 K 个已通过，补充轮次的 analyst+fact_checker 工作量约降至 (N−K)/N。典型 N=4~5、失败 1~2 时，第 2 轮最贵环节省约 **60–75%** |
| **质量** | 已通过答案不再被重生成，消除"对的变错"回退；失败子问题拿到增量证据后定向修订 |
| **风险** | ① 引用注册表必须**跨轮追加**、不可重排（否则报告引用错位）；② 部分重跑绕过整图，需确保 report_writer 拿到「复用 + 修订」的并集；③ 需要一次端到端验证多轮场景 |

### 2.4 落地档位

| 档位 | 改动量 | 效果 |
|------|--------|------|
| **A. 复用通过答案**（先做）| `research_runner` 合并逻辑 + 节点 `only_ids` 过滤 | 拿到主要提速与防回退收益 |
| **B. 证据增量累积** | A + Citation Registry 追加式跨轮 | 引用稳定、报告见全集，补证更充分 |

**建议**：A、B 一起做（B 是 A 的正确性前提——不追加式累积引用，合并后的报告会引用错位）。先在 `--max-rounds 2` 且必触发补充轮的任务（如 `benchmark/run_benchmark.py 04 10`）上验证。

### 2.5 验收

- 正确性：补充轮次后，已通过子问题的答案与引用**逐字不变**；报告引用全部命中注册表。
- 速度：对同一必触发补充轮的任务，对比改造前后第 2 轮 analyst+fact_checker 耗时（需先加节点计时打点，见下）。

### 2.6 实现记录（已落地）

实际实现比 2.2 的草案更简洁——**没有**给 `analyst_node` / `fact_checker_node` 加 `only_sub_question_ids` 参数，而是靠「构造只含失败子问题的 sub_state + 直接编排节点」达到同样效果，节点函数本身零改动即可复用：

- **失败集来源**：`fact_checker_node` 新增两个返回字段 `failed_sub_questions`（有严重问题的子问题 id）与 `follow_up_by_sq`（各失败子问题的定向补充 query），并写入 `ResearchState`。这就是"置信停止"的信号——failed 集为空即收敛。
- **增量编排**：`research_runner.py` 新增 `_supplement_round()`（仿 `_revise_citations` 的直接调节点风格），把 `sub_questions` 缩到失败子集、各自 `search_queries` 换成其 `follow_up_by_sq`，顺序跑 `retriever→content_extractor→source_evaluator→evidence_builder→analyst→fact_checker`（`_step()` 逐节点推进度/快照）。证据向量库按 `task_id` 天然跨轮累积。
- **答案复用**：合并时失败子问题用新答案覆盖，其余**原样复用**上一轮的 `sub_answers`（顺序不变）。
- **引用追加式（CID 跨轮稳定）**：`analyst_node` 改为**从 `state["citation_registry"]` 播种** `url_to_cid` 并令 `_cid_n = max+1`，在旧注册表上追加新来源。首轮 / 单轮时 prior 为空，行为与原来逐字一致；补证轮里旧 `C0x` 保持不变、新证据续新号，`sub_state` 的 registry 直接就是并集，无需另做合并。
- **报告**：补证发生时（`current_round>1`）在循环末尾用合并后的完整 `sub_answers` **重写一次**报告；未触发补证则沿用首轮图内生成的报告。
- **收敛/封顶**：`while` 循环条件改为「`fact_check_passed` 为真 → 停」「`failed_sub_questions` 为空 → 停」，封顶 `max_rounds`。

## 重点三：全局目标锚定（防跑偏 + 对准用户问题，零新字段）

### 3.1 问题：各节点各自为战，报告容易"答非所问"

多轮/多子问题并发下，每个节点只看到自己那一小块，容易偏离用户真正要的答案（尤其"评价/选型/建议"类问题被写成泛泛背景罗列）。

### 3.2 方案：复用已有的 `query` + `research_goal`，不新增状态字段

确认 `state["query"]` 已全局可用、`research_plan.research_goal` 槽位早已由 planner 产出且被 report_writer 读取——**无需新增 `task_goal` 字段**，只升级内容 + 接线 3 处提示词：

- **planner.md**：把 `research_goal` 从"一句话概括目标"升级为"**核心诉求 + 哪个是重点必答**"（评价/选型/建议/决策要显式点名），同一字段、内容更实。
- **report_writer**：`report_writer_node` 的 user 消息把「研究问题/研究目标」提到最前作为**行文主轴**，提示词新增原则"全文正面回应用户、结论前置、收尾回到原始诉求"。
  - **证据不足也必须回答（分层作答）**：reporter 直接可见用户原始 `query`。放宽原来"绝不外引"的硬规则为**分层**——有证据的结论照旧基于素材 + `[C0x]`；素材不足以回答核心问题时，允许用模型自身通用知识**正面作答**，但必须 *斜体* + 显式标注「基于通用知识的推断，暂无检索证据佐证」+ **绝不附引用号**（守住引用诚信底线）。避免"补充轮没捞到有效证据 → 报告以'证据不足'搪塞回避用户问题"。
- **fact_checker**：`_check_single_answer` 注入「研究总目标」作上下文，核查维度加一条"是否切题"——仅当出现与总目标和本子问题**均无关的跑题填充**才按 `insufficient_evidence` 标记（正常的局部回答不算跑题，避免误伤）。

零新依赖、零新状态字段，纯复用 + 提示词。

## 重点四：报告参数知识的受控使用（CoVe-lite 抗幻觉）

### 4.1 背景：放开"通用知识兜底"后新增的幻觉面

重点三让 report_writer 在证据不足时可用模型自身知识**正面回答**，但这是**唯一没有代码级围栏**的非证据出口，且 report_writer 是末节点、输出不再被核查。行业调研的关键事实：引用 ≠ 正确（顶级深度研究 Agent 事实核查准确率仅 39–59%，顶级 RAG 仍有 17–33% 幻觉）；最危险的不是"填空"而是模型用参数记忆**覆盖**检索到的正确证据（确认偏误 / 归因错配）。

### 4.2 方案：CoVe（方案丙）—— 核对与修订分离，核对调用压到最低

取 [Chain-of-Verification](https://arxiv.org/abs/2309.11495)（ACL Findings 2024）的"起草→核对→修订"骨架，**默认每篇全开**（召回稳定，不做启发式触发）。核对与修订**分两步**，把成本压在"核对"这一步：

1. **Pass 1 起草（照旧）**：report_writer 自然行文草稿，temp 0.45。
2. **Pass 2 核对（`_cove_detect_problems`，重点压最低）**：拿真实证据逐条核对，**只输出「一一对应的结构化问题清单」** `{"problems":[{quote,issue,fix}]}`（issue∈conflict/unsourced/overclaim/citation_mismatch，≤12 条），**不重写报告**。用两个杠杆压到最低：**关思维链**（`thinking:disabled`）+ **限 max_tokens**（1024）。
3. **Pass 3 修订（仅检出问题时，report_writer 重写）**：把问题清单塞进 report_writer 的 prompt，令其**依 fix 逐条最小修正、其余段落原样**，输出完整修订报告（LLM 在上下文里改，不怕字符串匹配失败）。无问题 → 跳过，直接用初稿。
4. **代码兜底（0 调用，`_sanitize_report_citations`）**：确定性剥离残留 `[C??]` / registry 外编号（硬围栏，对应审计发现①）。

**成本模型**：draft 恒 1 次；detect 恒 1 次（关思维链，实测输出仅 ~410 token）；revise 仅在检出问题时 +1 次（整篇输出）。即"多的那次"取其最便宜形态，整篇输出的代价只在真有问题时才付。

**三条不可退让原则**（源自调研）：证据至上 · 默认可否证 · CoVe 逐条对证据。

### 4.3 实测：核对调用「思维链 × 最大输出」对比

`rag_experiments/cove_verify_experiment.py`：同一份含 5 处已知错误的报告初稿 + 对照证据，网格对比（mimo-v2.5）。

| 思维链 | max_tok | JSON 完整 | 召回 | 输出 tok | 思维 tok | 延迟 |
|---|---|---|---|---|---|---|
| 关 | 256 | 0% | 0% | 256 | 0 | 5.0s |
| **关** | **512** | **100%** | **100%** | **409** | **0** | **5.9s** |
| 关 | 1024 | 100% | 100% | 421 | 0 | 7.9s |
| 开 | 256 | 0% | 0% | 256 | 255 | 4.6s |
| 开 | 512 | 0% | 0% | 512 | 511 | 10.5s |
| 开 | 1024 | 0% | 0% | 1024 | 1023 | 15.9s |

**结论（决定性）**：这次调用**必须关思维链**——开着时推理吃光整个输出预算（reasoning_tokens≈max_tokens），JSON 永远吐不完 → 召回 0%，且 token/延迟还翻 2–3×。关思维链后：256 太紧会截断（需 ~410），**512/1024 均 100% 召回**、无误报、输出仅 ~410 token。生产取 `thinking=False, max_tokens=1024`（1024 为安全上限，实际计费仍 ~410，给"问题多"的报告留余量防截断）。
> 附带发现：MiMo 思维链**默认开启**，而 analyst/fact_checker/report_writer 各调用当前都没显式关；它们 max_tokens=16384，思维链吃不光但仍按 ¥2/M 计入输出。是否对结构化抽取类节点也关思维链（需各自验证质量不掉），列为后续降本项。

### 4.3 为何不选其他方案

- probing 分类器区分参数/检索知识：需**白盒隐状态**，MiMo/OpenAI 兼容后端拿不到 → 不可用。
- SelfCheckGPT（N 次采样看一致性）：整篇长报告 N× 生成太贵 → 违背"少调用"。
- 结构化 claim 标注（模型逐条标 support 类型）：机器可检最强，但报告变模板化，**与 v0.2.1 主推的自然行文冲突** → 弃，仅借其"输出层可检"思想用在代码兜底。

### 4.4 实现锚点与验收

- `report_writer_node`（`nodes.py`）：draft → `_cove_detect_problems`（关思维链、限输出）→ 有问题则 report_writer 依清单重写 → `_sanitize_report_citations`。新增 `_cove_detect_problems` / `_COVE_PROBLEMS_RESPONSE_FORMAT` / `_COVE_DETECT_THINKING`、`_COVE_DETECT_MAX_TOKENS`；`LLMService.chat` 加 `thinking` / `extra_body` 透传；`app/prompts/report_verifier.md` 改为问题清单格式；实验脚本 `rag_experiments/cove_verify_experiment.py`。
- 验收：日志「Report CoVe: 检出 N 处问题，已依清单重写」；证据充分时 N=0（只花 detect 一次、不触发 revise）；核对调用 `reasoning_tokens` 恒为 0（思维链已关）。

## 重点五：全节点关闭思维链 + 冗余 max_tokens（降本提速）

### 5.1 背景：MiMo 思维链默认开，悄悄吞成本、废掉温度

探针实测（`reasoning_tokens`）：默认调用思维链**开着**——一句话小问题都烧 136 reasoning token（占输出 72%）。且**开思维链时 temperature/top_p 被强制为 1.0/0.95**（[MiMo 文档](https://mimo.mi.com/docs/en-US/quick-start/usage-guide/other/deep-thinking)），各节点设的 0.1/0.3/0.45 全失效——fact_checker 想要的 0.1 确定性核查实际在 1.0 上跑。

### 5.2 实验：各节点 思维链 on/off × 输出体量

`rag_experiments/node_thinking_experiment.py`（mimo-v2.5，真实提示词 + 代表夹具）：

| 节点 | 质量(关) | 质量(开) | 输出tok(关) | 思维tok(开) | 延迟 关→开 |
|---|---|---|---|---|---|
| planner | 100% | 100% | 659 | 1085 | 10→31s |
| analyst | 100% | 100% | 155 | **1599** | 3→27s |
| fact_checker | 100% | **0%（JSON坏）** | 739 | 794 | 11→22s |
| report_draft | 100% | 100% | 1160 | 733 | 19→34s |
| report_revise | 100% | 100%* | 233 | 1102 | 3→29s |

\* revise 开思维链会**越界重写整篇**（违反"最小修正"）；关思维链更守规矩。样本见 `results/node_thinking_samples.txt`。

**结论（决定性）**：思维链对这些任务**零质量增益**，却多烧 5–10× 输出 token、3–9× 延迟；fact_checker 开着还会把 JSON 包进 ```fence 或截断。→ **全节点关思维链**（连带恢复各节点本应生效的温度）。

### 5.3 落地：全节点 `thinking=False` + 冗余 max_tokens

`nodes.py` 六个 LLM 调用点全部 `thinking=False`；max_tokens 按"实测输出 max × 冗余、不卡刚好"设（关思维链后无推理争预算，该上限只兜失控）：

| 节点 | max_tokens | 依据 |
|---|---|---|
| planner | 2048 | 实测 659，留余量 |
| analyst | 2048 | 实测 155(medium)，deep≤800字约 1200，留余量 |
| fact_checker | 2048 | 实测 739，多 issue 留余量 |
| report_draft | 8192 | 夹具偏小(1160)，真实深报告 3–4K，给足 |
| report_revise | 8192 | 同 draft（整篇重写） |
| CoVe detect | 1024 | 见 4.3 |

> ⚠️ 关键顺序（detect 截断的教训）：**先关思维链，再砍 max_tokens**——思维链还开着时砍小，会被推理吃光、截断答案。
