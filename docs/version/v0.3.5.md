# 版本说明 v0.3.5

> 发布日期：2026-09-11 · 上一版本：[v0.3.0](v0.3.0.md) · 对比基线：commit `ebd8bf3`

v0.3.0 把部署形态定了下来，v0.3.5 回到检索链路本身：检索路由从「一个任务一个全局领域」下沉到「每个子问题自己的领域」，新增结构化学术数据源，混合检索（BM25 稀疏 + dense）时隔多轮否决后按查询自适应触发的方式重新上线。三条主线之外，还完整存档了一次结论为"不采用"的 GraphRAG 评测，以及一轮文档整理。

四条主线：

1. **检索路由：域驱动、粒度下沉到子问题** —— `retriever_node` 不再是"一个任务一个 domain"，Planner 给每个子问题单独标注 domain，垂直双路检索按子问题查表触发；新增 CrossRef + arXiv 两个结构化学术数据源，与通用检索互补。
2. **混合检索重新上线：查询自适应触发** —— BM25 稀疏 + dense 加性并集融合，经过 P1（RRF，否决）→ 三阶段离线/生产验证（否决）→ 黄金集扩充复核（发现此前否决结论是有偏样本的产物）→ 查询自适应门控实现（锚点查询 +11.9pp，非锚点查询零回归），共五轮验证后确认可上线。
3. **GraphRAG 评测终止** —— 完整四层评测 + 工程复核 + Global Search 补测，两轮独立测评均为负向结果，判定不进生产线，POC 代码/容器/环境已清理，仅保留评测结论存档。
4. **MySQL 连接池健壮性修复** —— worker 长时间空跑后连接被服务端悄悄断开导致的 `errno 2013`，补齐 `pool_pre_ping` + `pool_recycle`。

> 检索路由的完整过程（含中途被推翻的错误结论）见 [`检索路由蓝图.md`](../检索路由蓝图.md)；混合检索的五轮验证过程见 [`RAG改进方案.md`](../RAG改进方案.md) §六 与 `benchmark/GoldenDataset/improvement_plan.md`；GraphRAG 评测见 [`GraphRAG评测结论.md`](../GraphRAG评测结论.md)。

## 二、检索路由：域驱动，粒度下沉到子问题

旧版 `retriever_node` 的垂直双路检索按**整个研究任务**共用一个 `research_strategy.domain`，一次只能选一个域，general 域几乎打不到垂直源加成。对照 AnySearch 的调研（[`AnySearch技术原理与项目借鉴调研.md`](../AnySearch技术原理与项目借鉴调研.md)）确认这是根因后，改为：

- **Planner 逐个子问题标注 domain**（`app/prompts/planner.md` Sub-question Rules），`retriever_node` 按 `sq_id` 查表决定这条查询走哪路。domain 枚举从 6 个扩到 **11 个**（新增 `education` / `health` / `code` / `environment` / `security` 等，`environment` 替换掉规模不达标的旧 `ip`），除 `general` 外 10 个都在 `VERTICAL_ROUTES` 里有对应垂直路由。
- **真正跨两个域的子问题不强迫二选一**：Planner 标注 `domain_secondary` 后走 `search_vertical_multi`，两域垂直源都搜，不二选一（AnySearch 差距 #2 的补齐）。
- **接入 CrossRef + arXiv 两个结构化学术数据源**（`app/services/academic_api.py`）：academic 路由下额外并发查询，返回 DOI / 被引数 / 期刊 / 年份等结构化字段，与网页摘要互补——CrossRef 覆盖已发表文献，arXiv 覆盖前沿预印本。`app/models/source.py::SearchResult` 新增 `provider` / `search_route` / `doi` / `citation_count` / `venue` / `published_year` 字段承载来源元数据。
- **多路结果按规范标识符去重**：`_fuse_and_rank()` 改为优先按 DOI/arXiv ID 去重（而非 URL——同一篇论文在不同源下 URL 不同），再按 authority/diversity/freshness 加权排序。
- **CrossRef/arXiv 三层限速**：进程级 `asyncio.Semaphore` + 跨进程 Redis 令牌桶 + arXiv 熔断（命中 429 后冷却 360 秒直接跳过）。两个源限速机制本质不同——CrossRef 限瞬时并发连接数，arXiv 限短窗口累计请求数（约 20 个/7 秒），后者靠调小并发数无效，只能靠速率对齐官方限制。
- **第 2+ 轮补证同样吃这套路由**：`_supplement_round` 传入的 `sub_questions` 保留各自的 `domain`，不再退回顶层 domain。

实测：12 题基准总耗时 -7.4%，集中在 business/legal/policy 三个域；CrossRef 加限速后完整基准失败清零、总耗时收窄 25%；arXiv 加熔断后 429 次数从 67 降到 6、总耗时再收窄 12.4%。过程中一版因方法论缺陷把收益数字做虚高（最初汇报 -50%），已在文档中如实修正。

## 三、混合检索：BM25 + dense，查询自适应触发

这是本版本耗时最长的一条线，经过五轮验证：

| 轮次 | 方式 | 结果 |
|---|---|---|
| P1（历史） | dense + BM25，RRF 融合 | 否决：RRF 会把 dense 已召回的 gold 挤出去 |
| 阶段一 | 加性并集融合，离线理想化验证（`rank_bm25`） | 打平但未超过 dense@40 |
| 阶段二 | 生产路径验证（真实 Qdrant 稀疏向量） | 零增益，比理想化版本更差（collection 级 IDF 与离线 per-task IDF 有差异） |
| 阶段三 | 融合方式对比 + reranker 截断深度分析 | 全部否决，量化出 reranker 截断本身才是可优化的杠杆 |
| 黄金集扩充复核 | 扩充 120→162 题，新增 42 题精确锚点用例 | **推翻此前否决结论**：锚点类查询有真实 +11.9pp 增益，此前是黄金集构造本身系统性回避了精确字面匹配场景 |

黄金集扩充过程中自查出两处生成偏差：`build_golden_set.py` 的出题提示词明确要求"不要照抄原句"，导致首次生成的锚点问题里 35/42 条把锚点词本身都问没了，改写专用生成提示词（要求锚点词字面保留）后重新生成。

**最终生产实现**：查询自适应触发，而非全局开关。新增 `app/services/sparse_tokenizer.py::has_lexical_anchor()`，判断查询（含中译英后的译文）是否含精确标识符（产品型号/版本号/DOI/法条编号）。`rag_service.retrieve_evidence` 只有命中才触发 dense+sparse 加性并集、dense 预算收窄到 `hybrid_dense_k`；未命中的查询完全走原有纯 dense 路径，不受影响。

判定正则踩了一个坑：最初用 `\b` 做词边界，42 条锚点验证题里 20 条漏检——Python `\b` 按 Unicode `\w` 判断，中文字符也算 `\w`，"INT16量化""Article 9将"这类中英文直接粘连时 `\b` 在交界处不成立。改用 `(?<![A-Za-z0-9])` / `(?![A-Za-z0-9])` 负向环视后 42/42 正确触发。

生产路径最终验证（完全模拟 `retriever_node` 调用方式）：

| 子集 | n | Recall@6 |
|---|---|---|
| 锚点子集（精确标识符查询） | 42 | **0.9762**（vs 纯 dense@40 基线 0.8571，**+11.9pp**） |
| 原始子集（此前四轮验证过的 120 题） | 120 | **0.9000**（= 纯 dense@40 基线，**零回归**） |
| 全体 | 162 | **0.9198** |

`HYBRID_ENABLED` 默认改为 `true`：现在只决定"基础设施要不要打开"（Qdrant sparse 命名向量、ingest 是否计算 BM25 向量），不再直接决定"这次检索会不会用 sparse"——门控与预算收窄全部下沉到 `retrieve_evidence` 内部，与本项目已有的 `VERTICAL_ROUTES` 域驱动路由是同一设计哲学：按查询特征路由，不是全局一刀切。

## 四、GraphRAG 评测：结论为不采用，实验终止

2026-09-05 ～ 09-08，完整走完调研 → 选型 → 隔离验证 → 四层评测（L0 图构建质量 / L1 检索质量 / L2 推理质量 / L3 运营成本）→ 工程复核补齐 → Global Search 补测全过程。两轮独立测评（Local Search 多跳检索命中率、Global Search 综述覆盖率 graph=0.828 全面落后 dense=0.936）均为负向结果，判定不进生产线。

POC 代码目录 `graph_experiments/`、独立 Neo4j/Qdrant 容器、数据卷、conda 环境均已删除，唯一存档见 [`GraphRAG评测结论.md`](../GraphRAG评测结论.md)，重新评估的前提条件写在该文档 §7。

## 五、其他修复

**MySQL 连接池空闲断连**（`app/services/db.py::get_engine`）：worker 常年空跑，连接闲置超过 MySQL `wait_timeout` 会被服务端悄悄断开，池里拿到死连接执行首条 SQL 直接报 `errno 2013`——现象是空闲一段时间后提交的头一两个任务必失败。补齐 `pool_pre_ping=True`（取用前探活）+ `pool_recycle=1800`（连接活满 30 分钟主动换新），仅对非 sqlite 生效。
