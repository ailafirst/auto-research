# 版本说明 v0.3.0

> 发布日期：2026-08-07 · 上一版本：[v0.2.1](v0.2.1.md) · 对比基线：commit `9bd9917`

第二次**次版本号跳变**。v0.2.x 把系统从"单进程内存任务"推进到"模型服务 + API + N×worker"的服务形态，但那套服务**仍然是手工装在机器上的**：Nginx 解压在 `C:\nginx-1.28.0`、配置里写死项目绝对路径、Redis 靠一个单独的 compose 文件、worker 靠开多个终端各跑一条命令。

v0.3.0 把这些散在人记忆里的部署知识变成**仓库里可读、可 diff、可回滚的文件**。三条主线：

1. **容器化部署** —— 除模型服务外全部组件进容器，`deployment/start-all.ps1` 一条命令拉起。
2. **数据层落地** —— SQLite → MySQL（任务 SoR）、Qdrant 内存实例 → 独立服务（向量持久化 + TTL）。
3. **凭据与信息暴露收敛** —— 消除弱口令兜底，收敛公网可达的 `/health` 明细。

> 设计取舍与踩过的坑见 [`容器化部署.md`](../容器化部署.md)（本版核心 deep-dive，没用过 Docker 也能读）。照着跑的步骤在[根 README](../../README.md) A 节。

## 二、容器化部署

只有模型服务留在宿主机 —— 它要 GPU、7.1GB 权重、冷启动 100 秒，是有状态单例，和可随时重建的 api/worker 不是一类进程。

```
宿主机   model-server :8100  ←──┐  容器经 host.docker.internal 访问
                               │
容器     nginx :80 ──→ api ────┤
                   ↘  worker × N
                        ↘ mysql（任务 SoR） / redis（队列·缓存·限流） / qdrant（向量）
```

**应用镜像刻意不含 torch。** 镜像 723MB，装上 torch 要 +5236MB；更要紧的是 `rag_service` 那条"模型服务不可达就回退本地加载"的降级路径——装了 torch 它会**真的能跑**，于是每个 worker 各自默默装一份 bge-m3 把内存吃干净；不装则是明确的 `ImportError`，故障从静默变可见。依赖据此拆成三份。

**对外只有 `:80`。** mysql / redis / qdrant 各有一个**仅绑 `127.0.0.1`** 的调试映射（3307 / 6380 / 6334）——不写这个前缀时 Docker 默认绑 `0.0.0.0`，等于把基础设施暴露到局域网。api 无宿主机映射，只能经 nginx 访问。

**健康检查查"能不能用"不是"在不在"。** MySQL 原先用 `mysqladmin ping`——它**认证失败时也退出 0**，只能证明端口通，已换成实跑 `SELECT 1`。api 的检查只判"进程活着且能响应"：`/health` 恒返回 200，健康度在 body 的 `status` 里；否则 Redis 抖一下就会把一个完全可以降级运行的 API 判成 unhealthy 并重启。

`start-all.ps1` 成为唯一入口，最后一步逐项校验依赖，任何一项不通即报错退出：**降级是运行期的容错能力，不是一次成功部署的可接受终态。**

## 三、数据层

| 项 | 要点 |
|---|---|
| SQLite → MySQL | `tasks.data` 存完整任务 JSON。**MySQL 的 `TEXT` 只有 64KB**，故用 `Text().with_variant(LONGTEXT, "mysql")`。附幂等迁移脚本 `migrate_sqlite_to_mysql.py` |
| Qdrant 内存 → 远程 | 由 `QDRANT_MODE` 显式切换，不是"配了 URL 就用远程"；不可达自动回退内存，实际模式看 `/health` |
| upsert 分批 | 一个任务 2000+ chunk 会超请求体上限，而**失败会被当成「Qdrant 不可用」静默跳过整个证据构建**（任务照常完成、报告零引用）。故 256 一批 |
| 向量 TTL | `VECTOR_TTL_DAYS=7`，worker 内 arq cron 范围删除；配套建 `task_id` / `created_at` 的 payload 索引 |

## 四、凭据与信息暴露

**四个基础设施口令**（MySQL ×2 / Redis / Qdrant）在 `deployment/docker/.env`（不入库，首次启动生成随机值），compose 里一律 `${VAR:?...}` 而非 `${VAR:-默认值}`：**缺任何一个直接启动失败，不悄悄退回弱口令。**

> **规则：凡是把 DSN 交给日志或响应体的地方，必须先过 `app/core/config.py` 的 `mask_dsn()`。** 口令写在 URL 里，而 `/health` 经 Nginx 公网可达。

**`/health` 明细令牌。** `dependencies[].detail` 里是内部主机名、端口、库用户名、组件版本和失败时的异常原文——对排查有用，对公网访客则是白送的踩点信息。默认不返回，需带 `X-Health-Token`（`secrets.compare_digest` 常数时间比较）。

没按来源 IP 判内外网：本项目的公网入口是 frp 隧道，frpc 在宿主机回连 `127.0.0.1:80`，Nginx 看到的 `$remote_addr` 和本机访问一模一样，**IP 层面根本分不开**。

**探测客户端复用。** `/health` 原先每次调用新建一个 Qdrant client，实测 37–81ms；改为复用后稳定在 ~12ms。代价是状态粘滞——首次探测撞上 Qdrant 没起来，实例会永久回退内存模式，所以配置为 `remote` 而实例是 `memory` 时必须丢弃重建。实测停掉 qdrant → `degraded`，重启 → **2 秒内恢复 `remote`，无需重启 api 进程**。
