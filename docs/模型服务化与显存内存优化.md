# 模型服务化与显存 / 内存优化

> 日期：2026-07-17
> 主题：多 worker 测试崩溃的根因诊断，以及 FP16 量化 + 模型服务化两项修复，并解释显存 / 内存为何下降。

---

## 1. 问题：多 worker 测试把机器压崩

一次多 worker 基准测试中，测试报错、Claude Code 全部关闭，项目根目录留下一个 `bash.exe.stackdump`。

从 Windows 事件日志复原现场，找到决定性证据：

```
06:21:21  Event 2004 (Resource-Exhaustion-Detector)
  Windows successfully diagnosed a low virtual memory condition.
  消耗最多虚拟内存的进程：
    python.exe (20552) = 8.86 GB   ← API (uvicorn)
    python.exe (66724) = 6.90 GB   ← worker A
    python.exe (66528) = 6.87 GB   ← worker B
  三者合计 ≈ 22.6 GB

06:21:45  Event 153 (nvlddmkm)     ← NVIDIA 驱动错误 / 重置，24 秒后
```

时间线：两个研究任务入队 → 两个 worker 各领一个 → 系统**提交内存（commit）顶穿** → GPU 驱动出错 → **worker 66724 被 Windows 直接终止**（进程消失，数据库里任务僵死在 `source_evaluator` / 55%，`error=None`）。

关键否定证据：该 worker **没有任何 Python 异常，也没有原生崩溃日志**。`run_research` 的 `except` 一行都没跑到——它是在向系统申请内存时被硬毙的，这正是 commit 耗尽的特征。同一天此前已有 4 次同样的 Event 2004，说明是必然而非偶发；那个 `bash.exe.stackdump` 也是同一次内存耗尽的连带受害者。

这台机器：32 GB 物理内存，16 GB 显存的 RTX 4080 SUPER。

---

## 2. 先厘清一个关键区分：GPU 显存 ≠ 系统提交内存

这次崩溃最容易被误判的地方：**它不是 GPU 显存（VRAM）不够，而是系统提交内存（commit）顶穿。** 两者是完全不同的资源，混淆会导致修错方向。

| | GPU 显存 (VRAM) | 系统提交内存 (commit charge) |
|---|---|---|
| 归谁管 | 显卡，16 GB | 物理内存 + 页面文件(pagefile) 之和的“承诺”上限 |
| 存什么 | 模型权重、激活、CUDA 缓存 | 进程向系统申请的全部可写虚拟地址 |
| 顶穿后果 | CUDA OOM 异常（可捕获） | **Windows 拒绝分配 / 直接终止进程（不可捕获）** |
| 本次崩溃 | 未耗尽（4638 MB / 16 GB） | **耗尽（22.6 GB 三进程 + 系统基础 ≈ 顶穿 limit）** |

一个进程的 commit 远大于它的 GPU 占用，也远大于它的物理内存占用（RSS）。实测一个加载了全部模型的进程：

- GPU 显存：4638 MB
- 物理内存 RSS：约 1900 MB
- **commit：6900 MB** ← 就是这个数字乘以进程数，顶穿了系统

所以真正的瓶颈变量是**建了几个满配模型进程**，不是模型多大、也不是显卡多小。

---

## 3. 根因拆解：每个 worker 的 6.9 GB 是怎么堆出来的

逐步实测单个进程加载三个模型时的 commit 增量（`PrivateUsage`，CUDA + fp32）：

| 步骤 | commit 增量 |
|---|---|
| `import torch`（仅导入，零模型） | **+1129 MB** |
| `import transformers` | +827 MB |
| CUDA context + cuBLAS/cuDNN kernel 懒加载 | +1121 MB |
| bge-m3 加载 | +2105 MB |
| bge-reranker-v2-m3 加载 | **+3454 MB** |
| opus-mt 加载 | +472 MB |
| **单进程合计** | **≈ 6.9 GB** |

两个隐藏的大头值得注意：

1. **光是 `import torch` + `import transformers` 就要约 1.9 GB**，一个模型都还没加载。
2. **CUDA context 税约 1.7 GB**（CUDA + fp32 进程 9192 MB，纯 CPU 进程 7466 MB，差值即此），这是任何进程第一次碰 GPU 都要付的固定开销。

旧架构下，每个 worker 进程都要把上面这 6.9 GB **完整付一遍**，进程间零共享（Windows 用 spawn 而非 fork，无法写时复制共享权重）。于是：

| worker 数 | 旧架构 commit | 说明 |
|---|---|---|
| 1 | 15.8 GB | + API 8.86 + worker 6.9 |
| 2 | **22.6 GB** | 就是崩溃的那次 |
| 4 | 36.5 GB | 早就装不下 |

顺带发现一个纯浪费：由于队列已启用、研究流程全在 worker 执行，**API 进程那 8.86 GB 模型从头到尾没被用到**——它预热了一套永远不会调用的模型。

## 4. 方案一：FP16 量化（先把单份模型压小）

模型默认以 fp32 加载。改 fp16 可把权重显存减半。在 120 题黄金集上实测精度影响（评测口径与 `rag_experiments/run.py` 一致，只改精度一个变量）：

| 指标 | FP32 | FP16 | Δ |
|---|---|---|---|
| **Recall@6**（rerank 后） | 0.8917 | 0.9000 | +0.0083（+1 题，噪声内） |
| Recall@40（向量召回上限） | 0.9167 | 0.9167 | 持平 |
| NDCG@6 | 0.7776 | 0.7744 | −0.0032 |
| MRR | 0.7381 | 0.7311 | −0.0069 |
| **GPU 显存** | 4332 MB | **2166 MB** | **−50%** |
| 索引 embed 耗时 | 120s | 45s | −62%（2.7×） |

12 个任务里 11 个逐题完全一致，差异远在二项噪声内。**结论：fp16 检索质量无损，显存减半、速度翻倍。**

为什么质量无损：reranker 会把召回的 top-40 全部重新打分再排序，fp16 带来的 ~1e-3 扰动不足以把正确 chunk 挤出 40 名开外——召回集合不变，最终 top-6 就不变。

复现：`python rag_experiments/experiment_fp16.py --both --save`

> 过程中还修掉一个真 bug：embedding 缓存键原本是 `(模型, 维度, 文本)` 不含 dtype，导致切换精度会静默命中旧精度的向量。已在键中加入 `model_dtype`。

配置项：`.env` 的 `MODEL_DTYPE=fp16`（仅 cuda 生效，cpu 下 half 算子多不支持，自动退回 fp32）。

## 5. 方案二：模型服务化（让所有 worker 共享一份模型）

FP16 把单份模型压到 2.4 GB，但 2 个 worker 仍是 2 份。真正的解法是**把三个模型收敛到一个独立进程，worker 只发 HTTP 请求**。

```
                        ┌─────────────────────────────┐
                        │  model_server (:8100)        │
                        │  GPU 独占一份 fp16 模型：      │
   ┌── HTTP /embed ───▶ │    bge-m3 + reranker         │
   │   /rerank          │    + opus-mt                 │
   │   /translate       │  commit ≈ 7.3 GB（只此一份）  │
   │                    └─────────────────────────────┘
   │
┌──┴────┐   ┌───────┐   ┌───────┐   ┌───────┐
│  API  │   │worker1│   │worker2│   │worker3│  ← 全部不 import torch
│0.76GB │   │0.75GB │   │0.75GB │   │0.75GB │     不建 CUDA context
└───────┘   └───────┘   └───────┘   └───────┘
```

实现要点（全部遵循「降级安全」——模型服务不可达时自动回退本地加载，不构成单点故障）：

- 新增 `app/model_server.py`：独立 FastAPI 进程，启动即预热三个模型，暴露 `/embed` `/rerank` `/translate` `/health`。复用现有的懒加载 + 串行锁 + fp16 逻辑，实现只有一处。
- `rag_service.py` / `translation_service.py`：`model_service_url` 非空时走 HTTP，异常时回退本地（与 Redis 缓存 / arq 队列同样的降级风格）。
- `main.py`：队列已就绪或配置了模型服务时，API 进程**跳过本地模型预热**，省掉那 8.86 GB。

**实测服务化 worker 的 commit = 758 MB**，且全程 `torch` / `transformers` 从未进入 `sys.modules`。之所以能降到 1/9，正是因为它不再付第 3 节里那 6.9 GB 的任何一项——不导入 torch、不建 CUDA context、不加载任何权重。（这 758 MB 里还有 687 MB 是 `qdrant_client` 连带拉进来的 `fastembed`，与本方案无关。）

## 6. 为什么显存 / 内存降低（汇总）

两条线各自解决一个资源：

**GPU 显存（靠 FP16）：** 一份模型权重从 fp32 的 4638 MB 减半到 fp16 的 ~2166 MB。

**系统提交内存（靠服务化）：** 这才是避免崩溃的关键。旧架构下 6.9 GB 的进程成本 = torch 导入 + CUDA context 税 + 三份权重，**每个 worker 各付一遍**；服务化后这笔成本只在 model_server 进程付一次，worker 降到 0.75 GB。于是 worker 的边际成本从 6.9 GB 变成 0.75 GB——内存占用从「随 worker 数线性增长 O(N)」变成「一份固定成本 + 极小的每 worker 增量」。

综合对照（本机实测）：

| 配置 | 旧架构 commit | 新架构 commit（fp16 + 服务化） |
|---|---|---|
| 1 worker | 15.8 GB | 8.8 GB（模型服务 7.3 + API 0.76 + worker 0.75） |
| 2 worker | **22.6 GB（崩溃）** | **9.6 GB** |
| 4 worker | 36.5 GB | 11.1 GB |
| 每加 1 worker | +6.9 GB | **+0.75 GB** |

GPU 显存：模型服务独占一份 fp16 模型，约 2.4 GB VRAM（旧架构 API + 2 worker = 3 份 fp32 = 约 13 GB）。

## 7. 多 worker 验证（复现当初崩溃的场景）

用当初报错的同一场景压测：burst 齐发 4 个任务、2 个 worker、`--max-rounds 2`（让核查未通过的任务触发补充轮次）。

```
python benchmark/run_benchmark.py 03 10 04 09 --mode burst --max-rounds 2
```

结果：

| 指标 | 结果 |
|---|---|
| 完成 | **4 / 4**，零失败、零 timeout、**零进程崩溃** |
| 跨进程分摊 | **✓** 2 个 worker 都参与（各领 2 个任务，正好 `WORKER_MAX_JOBS=2`） |
| 峰值并行度 | 4 |
| 加速比 | 2.36× vs 串行 |
| makespan | 229 s |
| 补充轮次 | 04、10 核查未通过 → **自动跑第 2 轮**；03、09 通过 → 第 1 轮结束 |

内存全程曲线（对照上次同场景的 22.6 GB 崩溃）：

| 时刻 | worker1 | worker2 | 系统 committed | 物理 RAM 可用 |
|---|---|---|---|---|
| 启动 | 754 MB | 754 MB | 40.6 GB | 10.2 GB |
| 满载 (T+75s，峰值并行 4) | 1020 MB | 1019 MB | 41.2 GB | 10.5 GB |
| 完成 | 1009 MB | 1020 MB | 41.5 GB | 10.6 GB |

两个 worker commit 几乎相同（负载均衡的旁证），满载也只涨到约 1 GB。系统 committed 逼近 limit 时 Windows 按需扩了 pagefile（38.9 → 42.7 GB），物理内存始终有 10 GB 余量——**渐进的小额增长给了系统扩容的时间**，这正是不再重演「6.9 GB 单次分配瞬间顶穿」的原因。

## 8. 部署方式变更

多 worker 部署现在需要先起模型服务：

```bash
# 1. 模型服务（GPU 独占一份 fp16 模型，先起）
uvicorn app.model_server:app --host 0.0.0.0 --port 8100

# 2. API
uvicorn app.main:app --port 8000

# 3. worker（可开多个，各自 ~0.75 GB）
arq app.worker.WorkerSettings
```

`.env` 关键项：

```ini
MODEL_DTYPE=fp16                          # 本地模型精度（仅 cuda 生效）
MODEL_SERVICE_URL=http://127.0.0.1:8100   # 空则各进程本地加载（回退路径）
```

`MODEL_SERVICE_URL` 为空时，所有调用自动回退本地加载，功能不受影响——单机开发无需另起模型服务。

真正的横向扩展形态是「每机 / 每卡一个模型服务 + 若干 worker」；单机上 worker 边际成本已降到 0.75 GB，可按内存余量自由增减。
