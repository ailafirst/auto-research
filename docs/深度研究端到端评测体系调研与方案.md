# 深度研究端到端评测体系调研与方案

> 状态：调研结论与后续方案，尚未实现。  
> 记录日期：2026-08-13。

## 1. 结论

现有黄金集和 RAGAS 指标应继续保留，但它们只能回答“检索到的上下文是否相关、生成答案能否由上下文支撑”，**不能独立说明一项深度研究任务是否完成得好**。

深度研究的行业评测正在从单一问答正确率或总体 LLM-as-a-Judge 分数，转向以下分层体系：

```text
任务结果（是否完成用户目标）
├─ 证据与引用（结论是否可验证）
├─ 研究过程（检索、补证、失败恢复是否有效）
├─ 交互与修订（面对歧义/反馈能否调整）
└─ 运营效率（成本、时延、成功率）
```

本项目的优先方向不是立刻接入大型外部基准，而是先建立一个可重复运行的**端到端评测 MVP**：扩充任务集，并为每题配套人工审阅的原子化 rubric、关键声明和引用要求。之后再用外部基准做横向验证。

## 2. 当前基础与缺口

### 已有能力

| 层级 | 现有资产 | 可回答的问题 |
|---|---|---|
| RAG 回归 | `benchmark/GoldenDataset/golden_set.json`：12 个冻结语料任务 | 同一语料下检索质量是否回退 |
| RAG 质量 | `benchmark/test_rag.py`：Faithfulness、Context Precision、检索分数、证据缺口 | 回答是否能由已检索 context 支撑 |
| 节点诊断 | `test_planner.py`、`test_analyst.py` | Planner 与节点输出是否可人工检查 |
| 运行负载 | `run_benchmark.py` | 成功率、吞吐、队列等待、端到端延迟、worker 并行度 |

### 仍未覆盖的核心问题

1. 最终报告是否完整满足用户的显式与隐含要求。
2. 报告中的关键结论、数值和比较是否被对应引用真正支持。
3. 多源证据是否被正确综合，而非逐条拼接或只覆盖容易找到的部分。
4. 研究链路是否存在无效重复搜索、已发现信息遗忘、无效补证或错误收敛。
5. 复杂、歧义、时效性、证据冲突和网页失败等真实任务形状下是否仍稳定。
6. 后续引入多 Agent 后，质量提升是否值得额外 token、外部调用与时延成本。

因此，“扩充数据集”不能只增加语料和查询；每一个端到端任务都需要可审计的完成标准。

## 3. 外部调研：其他深度研究系统如何评测

### 3.1 浏览能力与过程轨迹

[BrowseComp](https://openai.com/index/browsecomp/) 将问题设计为“难找但易验证”的短答案，用于隔离测试持续浏览、检索策略与事实定位能力。它覆盖的是深度研究的底座能力，不评测长报告质量、引用组织或用户意图满足。

FutureSearch 的 [Deep Research Bench](https://arxiv.org/abs/2506.06287) 更接近端到端研究：使用冻结网页的 RetroSearch 环境避免实时 Web 漂移，并对长轨迹检查三类过程失败：

- 幻觉；
- 重复或无效的工具调用；
- 已经观察到的信息在后续推理中被遗忘。

启示：生产回归应至少保留一组冻结环境任务，不能完全依赖实时 Web；同时应保存搜索词、点击/抓取、补证轮次等 trace，才能定位“报告变差”究竟来自检索、分析还是流程控制。

### 3.2 最终报告与任务完成度

[DeepResearch Bench](https://arxiv.org/abs/2506.11763)（100 个跨 22 领域、以真实查询分布校准的任务）提出 RACE：对报告评估完整性、深度、指令遵循与可读性；同时用 FACT 评估引用准确度和有效引用数量。其核心价值是：报告质量与引文质量分开衡量，避免“文字写得好”掩盖证据不足。

[DeepResearch Bench II](https://github.com/imlrz/DeepResearch-Bench-II) 将专家报告拆为 9,430 条细粒度、可验证的 rubric，分成三类：

- 信息召回：是否找齐回答任务所必需的事实；
- 分析：是否据证据形成合理结论；
- 呈现：是否结构化、可读、易核验。

每条 rubric 是原子化的单点检查，而非模糊的“报告质量好不好”。该方法特别适合作为本项目端到端评测的设计参考。

[ResearchRubrics](https://evalscope.readthedocs.io/en/latest/benchmarks/researchrubrics.html) 使用 101 个开放研究任务与 2,593 条带权重的专家 rubric，覆盖显式/隐含要求、信息综合、引用、沟通与指令遵循。它进一步区分必须项、可选加分项和负向标准，适合处理开放式报告不存在唯一“标准答案”的事实。

[ReportBench](https://arxiv.org/abs/2508.15804) 以专家综述为参照，单独检查引用文献的质量与相关性、引用对声明的忠实性，以及未引用声明的真实性。这与本项目的 Citation Registry 和 CoVe 机制直接相关。

### 3.3 真实用户、交互与修订

[LiveResearchBench](https://livedeepresearch.github.io/) 强调任务应同时具备用户导向、时效性、无歧义和多面/搜索密集四个特征，并分别公开呈现结构组织、事实与逻辑一致性、覆盖度、引用关联度。

[IDRBench](https://www.alphaxiv.org/abs/2601.06676) 把“何时需要澄清、澄清是否提升意图对齐、交互代价是否合理”作为独立能力；这说明当前只评单轮自动运行仍不完整，但此项可放入第二阶段。

[Mr Dre](https://github.com/BaleChen/Mr-Dre) 则评测接收内容、格式和自反思反馈后的报告修订能力。项目已有事实核查后的补证机制，未来可将“补证/修订前后 rubric 的变化”纳入此类评测。

## 4. 建议的端到端评测 MVP

### 4.1 任务集分层

| 子集 | 是否冻结 | 目的 | 首批优先级 |
|---|---:|---|---:|
| RAG 回归集 | 是 | 保留现有语料任务，检测切片、向量、重排与检索回归 | 已有，持续维护 |
| 端到端报告集 | 推荐冻结证据快照 | 检查任务完成度、分析、引用与格式 | 最高 |
| 过程压力集 | 冻结 + 可控故障 | 测试证据冲突、稀缺、重复搜索、抓取失败和补证 | 高 |
| 实时 Web 哨兵集 | 否 | 观察最新信息、搜索服务和网页变化造成的真实表现 | 中 |
| 交互/修订集 | 冻结 | 测试澄清、用户反馈与报告修订 | 第二阶段 |

冻结集保证回归可重复；实时集用于发现生产环境退化。两者的结果必须分开报告，不能混为一个总分。

### 4.2 首批任务形状

端到端任务不应只重复现有“技术知识解释”主题。首批应平衡至少四类形状：

1. **单主题解释型**：验证直线链路不劣化，作为最低成本基线。
2. **多维比较/决策型**：要求比较表、条件化建议和明确取舍，验证规划与综合。
3. **时效与证据冲突型**：来源相互矛盾或观点快速变化，验证信源质量、冲突披露与谨慎结论。
4. **证据稀缺/网页失败型**：关键页不可抓取、搜索结果不足或低质量，验证降级、增量补证和不确定性披露。

每类均应同时覆盖中文任务和英文来源任务；对于涉及法规、金融、医疗等高风险领域，先只作为“风险披露与引用完整性”测试，不将系统定位为专业意见工具。

### 4.3 单题数据结构

建议每道端到端任务包含以下信息；这是数据格式提案，尚未落地：

```text
task_id / title / user_prompt / language / task_shape
evidence_snapshot（可选：冻结来源、抓取日期、允许域）
rubrics[]
  - id / dimension / description / weight / required
  - polarity: positive | negative
  - expected_evidence_type（事实、比较、推理、格式、引用）
key_claims[]（关键结论与可接受误差范围）
required_output（报告类型、长度、表格/建议/风险披露等）
fault_injection（可选：失效 URL、冲突来源、限额）
```

建议每题先写 8–15 条人工审阅 rubric，而非一开始追求大规模。设计要求：

- **原子化**：一条只验证一个事实、推理或交付要求；
- **可观察**：能从报告或引用中找到支持/缺失证据；
- **有权重**：必须项缺失应显著扣分；
- **含负向项**：例如无来源的精确数据、错误引用、无视用户约束、编造来源；
- **不绑定唯一措辞**：允许正确的不同写法和合理的替代来源。

## 5. 指标体系

### 5.1 结果层：任务是否完成

| 指标 | 定义 | 说明 |
|---|---|---|
| 加权 rubric 覆盖率 | 满足的正向 rubric 权重 / 全部正向权重 | 主指标 |
| 必选项通过率 | 满足的 required rubric 数 / required 总数 | 应与总分并列展示，不被平均分掩盖 |
| 负向错误率 | 命中的负向 rubric 数 / 负向 rubric 总数 | 例如编造、错误比较、忽略约束 |
| 指令遵循率 | 输出格式、语言、长度、指定交付物的满足率 | 可优先使用规则检查 |
| 分析得分 | “比较、因果、取舍、建议”等分析 rubric 的加权得分 | 与事实召回分开 |

### 5.2 证据层：结论是否可信

| 指标 | 定义 |
|---|---|
| 关键声明引用覆盖率 | 有有效引用的关键声明 / 全部关键声明 |
| Citation support rate | 被引用页面确实支持对应声明的引用 / 被抽检引用 |
| Citation precision | 关联到声明的引用中，真正相关且支持的比例 |
| 来源质量分布 | 一手/权威、学术、机构、媒体、聚合/博客等来源占比 |
| 冲突披露率 | 存在冲突证据时，报告有呈现差异或不确定性的比例 |

现有 RAGAS Faithfulness 应继续保留，但仅表示“基于传入 context 的推导性”；它不能替代对网页原文和最终引用关系的检查。

### 5.3 过程层：系统是否研究得有效

| 指标 | 目的 |
|---|---|
| 搜索重复率 | 发现无效重复查询或已知无结果路径反复执行 |
| 有效来源率 | 被最终引用或实际支撑答案的来源 / 全部抓取来源 |
| 补证命中率 | 进入补证后新增通过的 failed rubric / 初始失败 rubric |
| 收敛效率 | 达到通过状态所需研究轮数、搜索数和抓取数 |
| 遗忘率 | 轨迹中已获得关键事实却未用于最终报告的比例 |
| 故障恢复率 | 注入网页/搜索/向量库故障后仍完成可接受报告的比例 |

该层为未来评估 supervisor-worker 的必要前置：只有同时记录质量提升与额外搜索、LLM 调用、token 后，才能判断多 Agent 是否值得。

### 5.4 运营层：质量代价是否可接受

每次基准运行记录并按任务形状分组统计：

- 成功率、失败原因、降级路径；
- 端到端时延（mean、P50、P95）；
- LLM 输入/输出 token、请求数、模型费用估计；
- 搜索/抓取/API 调用数、缓存命中率；
- Worker 吞吐、队列等待、峰值并发。

报告结果时不建议压成单一总分。至少同时显示“必选项通过率、引用支持率、端到端时延、成本”。

## 6. 评分实现原则

1. **规则优先，LLM judge 补足开放判断。** 格式、语言、引用编号存在性、链接可访问性、数值范围等尽量确定性检查；内容综合、推理质量再用 LLM judge。
2. **评审模型与被测模型隔离。** 避免同模型自评偏好；抽样采用人工双评，计算与 judge 的一致性。
3. **输出证据而非只输出分数。** 每条 rubric 必须留下“报告中的支持片段、判定原因、相关引用”，便于复盘。
4. **固定评测版本。** 记录任务集版本、证据快照日期、系统 commit、模型/提示词/配置、judge 版本。
5. **多次运行。** LLM 非确定性任务至少重复运行，报告均值与波动；高成本任务可先做小样本 smoke test。
6. **防止指标投机。** 引用数量不是质量；长报告不是完整；检索更多不是研究更好。因此以 required rubric、引用支持与成本共同约束。

## 7. 分阶段实施建议

### 阶段 A：设计与数据扩充（下一步）

- 定义端到端任务 JSON Schema；
- 选取首批跨四种任务形状的任务；
- 为每题编写、审阅 rubric、关键声明和负向项；
- 为冻结任务保存合法可用的证据快照与元数据；
- 不改变生产流程，只建立基线。

### 阶段 B：端到端评测器

- 运行完整 `research_runner`，捕获报告、Citation Registry、事实核查结果和运行 trace；
- 实现规则检查、rubric judge、声明—引用抽检和成本统计；
- 输出逐题 JSONL 与聚合报告，能链接回证据片段。

### 阶段 C：过程与鲁棒性

- 加入重复搜索、遗忘、补证命中和故障恢复指标；
- 加入冻结 Web 环境或项目内证据快照；
- 将实时 Web 任务作为单独的生产哨兵，不与确定性回归混算。

### 阶段 D：交互与多 Agent 对比

- 对歧义任务评估澄清问题的必要性、收益与交互成本；
- 针对线性链、并行 worker、supervisor-worker 使用同一任务集 A/B 测试；
- 设定放量门槛：质量或引用支持率提升必须超过预设阈值，且成本、P95 时延不超过预算。

## 8. 当前不做的事

- 不以外部排行榜总分替代项目自身回归集；外部数据分布、语言、网页环境与成本条件不同。
- 不把实时 Web 结果和冻结集结果混在同一质量结论中。
- 不在没有端到端基线前直接用多 Agent 架构替换线性链。
- 不依赖单一 LLM judge 的总体主观分数。
- 不将“引用数更多”误判为“研究更可靠”。
