# 版本说明 v0.2.0

> 发布日期：2026-07-17 · 上一版本：[v0.1.6](版本说明_v0.1.6.md) · 对比基线：commit `9f5c644`

首个**次版本号跳变**。v0.1.x 全程在打磨单机、单进程内的研究质量（RAG 检索、analyst、事实核查）；v0.2.0 把系统从"单进程内存任务"推进到**可多 worker 并发、可产品化的服务形态**，三条主线：

1. **多 worker 服务化** —— Redis/arq 队列 + SQLite 记录层 + 分布式限流，API 与研究执行解耦。
2. **模型服务化 + FP16** —— 三个本地模型收敛到独立进程共享，修掉多 worker 顶穿系统内存的崩溃根因；显存减半、索引提速 2.7×。
3. **React 前端 + 过程透明** —— 用 Vite+React+TS 前端替换 Streamlit，实时进度、多轮可视化。

> 模型服务化的完整根因诊断与实测数据见 [`模型服务化与显存内存优化.md`](模型服务化与显存内存优化.md)（本版核心技术 deep-dive）。

## 二、多 worker 服务化

把系统从"单进程内存任务"推进到"可多 worker 并发执行"。核心运行链路：

```text
FastAPI 接单
  → SQLite 创建任务记录（SoR）
  → Redis/arq 队列派发任务
  → worker 执行 LangGraph 研究流程
  → Redis 写热进度（跨进程实时查询）
  → SQLite 写任务结果与最终报告
  → API 查询状态 / 详情 / 报告
```

**Redis 四类职责**（均"降级安全"——不可用时自动旁路，不阻断研究流程）：

| 能力 | 代码位置 | 说明 |
|------|----------|------|
| 搜索缓存 | `search_service.py` | 缓存 Tavily/DDG 结果，降外部 API 压力 |
| Embedding 缓存 | `rag_service.py` | 确定性 embedding 跨任务复用（缓存键含 `model_dtype`）|
| 热进度缓存 | `task_service.py` | 运行中状态/进度/轮次写 Redis，跨进程可读 |
| 分布式限流 | `rate_limiter.py` | Lua 令牌桶限制多 worker 下全局 LLM 速率 |

**SQLite 作系统记录层**：`tasks` 表存状态/查询/时间/完整 JSON，开启 WAL + busy_timeout 支持单机多 worker 共享。多机部署前可经 `DATABASE_URL` 切 MySQL/PostgreSQL，任务服务代码不需大改。

**队列与 worker**：任务优先入 arq 队列，独立 `arq app.worker.WorkerSettings` 进程消费，多 worker 共享队列自动分摊；队列不可用时回退 `asyncio.create_task` 进程内执行。API 由此保持轻量，耗时研究流程交给 worker 池。

## 三、模型服务化 + FP16（本版核心）

> 详见 [`模型服务化与显存内存优化.md`](模型服务化与显存内存优化.md)。此处为版本层摘要。

**触发**：一次 2-worker 基准测试把机器压崩（`bash.exe.stackdump`、worker 被 Windows 硬毙、任务僵死无异常）。事件日志复原：三进程 commit 合计 **22.6 GB 顶穿系统提交内存**（非 GPU 显存），GPU 驱动出错、worker 进程被直接终止。

**关键区分**：崩的是**系统提交内存（commit）**不是 GPU 显存——前者顶穿后 Windows 不可捕获地终止进程。旧架构每个 worker 各付 6.9 GB（torch 导入 1.9 GB + CUDA context 税 1.7 GB + 三份权重），进程间零共享。

**两条修复线**：

| 修复 | 手段 | 效果 |
|------|------|------|
| FP16 量化 | `MODEL_DTYPE=fp16`（仅 cuda）| GPU 显存 4638→2166 MB（**−50%**）、索引 embed 120s→45s（**2.7×**）；120 题检索质量无损（Recall@6 0.892→0.900，噪声内）|
| 模型服务化 | `app/model_server.py` 独立进程共享 bge-m3 + reranker + opus-mt | worker commit **6.9 GB → 0.75 GB**；每加 1 worker 边际成本 6.9→0.75 GB |

**内存对照（本机实测）**：

| 配置 | 旧架构 commit | 新架构（fp16 + 服务化）|
|---|---|---|
| 2 worker | **22.6 GB（崩溃）** | **9.6 GB** |
| 4 worker | 36.5 GB | 11.1 GB |
| 每加 1 worker | +6.9 GB | **+0.75 GB** |

均遵循"降级安全"：`MODEL_SERVICE_URL` 为空时所有调用自动回退本地加载，单机开发无需另起模型服务。

## 四、React 前端 + 过程透明

用 **Vite + React 19 + TypeScript** 新建 `web/` 前端，替换仅适合验证的 Streamlit：

- 任务创建（问题/轮次/报告类型/语言/搜索深度）、任务列表（历史/状态/耗时）、任务详情（实时进度/节点阶段/错误）、报告阅读（Markdown 渲染/引用/导出）。
- **过程透明**：Stepper 展示八节点流水线阶段，活跃步骤自动展开。
- **多轮可视化**：补充调查轮次以时间线（RoundTimeline）呈现，"第 N 轮 · 当前步骤"标签，解决此前"补充调查后进度条清零"的困惑。
- 前端全程走**相对路径 API**，天然适配 Nginx 反向代理，部署零改动。

前端设计以最小依赖为准（详见 `web/README.md`）。进度当前为轮询，SSE/WebSocket 实时推送列为后续（见 v0.2.1 方向）。

## 五、部署形态变更

多 worker 部署需先起模型服务：

```bash
uvicorn app.model_server:app --port 8100   # 1. 模型服务（GPU 独占一份 fp16 模型，先起）
uvicorn app.main:app --port 8000           # 2. API
arq app.worker.WorkerSettings              # 3. worker（可开多个，各 ~0.75 GB）
```

上线拓扑（应用全栈本地跑 + 云端仅内网穿透）见 [`部署方案.md`](部署方案.md)。

## 附录 A：为什么选 React 而不引入 Node 后端

当前真正缺的是**产品化前端和实时进度体验**，不是第二套后端。核心研究链路（LangGraph / RAG / embedding / reranker / 搜索抓取 / LLM / worker）高度依赖 Python 生态，Redis/SQLite/arq 已解决主要并发瓶颈，再引入 Node 后端只会增加部署/认证/日志/一致性复杂度。

Node.js 暂时**只作前端构建环境**。仅当出现多前端 API 聚合、复杂权限/OAuth 编排、大规模实时连接、或需 SSR/Next.js 时，才评估引入 **Node BFF（只做认证/聚合/实时连接，不碰研究核心）**。

## 附录 B：已知遗留问题 / 后续

1. **Qdrant 仍为内存模式**：研究任务内可用，进程重启丢向量索引；跨任务知识库需改持久 Qdrant。
2. **Redis 多职责**：缓存/队列/热进度/限流都压在 Redis，生产需监控内存、淘汰策略、连接数。
3. **进度仍为轮询**：SSE/WebSocket 实时推送、报告流式生成列入 v0.2.1。
4. **API 无鉴权**：公网暴露前需加鉴权（见部署方案的安全章节）。
5. **报告结构偏模板拼接**：模块化装配缺乏自然行文——列为 v0.2.1 重点优化方向。
