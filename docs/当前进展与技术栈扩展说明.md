# 当前进展与技术栈扩展说明

> 日期：2026-07-16  
> 主题：项目当前结构、高并发 Redis/SQLite 改造进展，以及 React / Node.js 扩展建议

## 1. 项目当前定位

Deep Research Agent 是一个基于 LangGraph、RAG、FastAPI 的自动化深度调研系统。用户提交研究问题后，系统自动完成：

1. 问题规划与子问题拆解
2. 联网搜索与网页内容抓取
3. 信源评估与证据索引构建
4. RAG 检索、分析、事实核查
5. 结构化 Markdown 报告生成

当前核心能力仍集中在 Python 后端：LangGraph 工作流、LLM 调用、搜索抓取、RAG、事实核查和报告生成都在 `app/` 内完成。现有 UI 为 Streamlit，适合开发验证，但不适合长期产品化交互。

## 2. 当前整体结构

```text
app/
  api/                 FastAPI 路由
  core/                配置、日志、异常
  graph/               LangGraph 状态、节点、图构建
  models/              Pydantic 数据模型
  prompts/             Planner / Analyst / Fact Checker / Report Writer 提示词
  services/            搜索、抓取、RAG、LLM、缓存、队列、数据库、任务服务
  main.py              FastAPI 应用入口
  worker.py            arq worker 入口

ui/
  streamlit_app.py     当前轻量 Web UI

benchmark/
  run_benchmark.py     高并发 / 多 worker 基准入口
  *_benchmark.py       Planner / Retriever / Analyst / RAG 专项评测

docs/
  PRD、架构文档、RAG 改进方案、版本说明等
```

核心运行链路：

```text
FastAPI 接单
  -> SQLite 创建任务记录
  -> Redis/arq 队列派发任务
  -> worker 执行 LangGraph 研究流程
  -> Redis 写热进度
  -> SQLite 写任务结果与最终报告
  -> API 查询状态 / 详情 / 报告
```

## 3. 刚完成的高并发 Redis / SQLite 改造

本轮改造已经把系统从“单进程内存任务”推进到“可多 worker 并发执行”的结构。

### 3.1 Redis 的职责

Redis 当前承担四类职责：

| 能力 | 代码位置 | 说明 |
|------|----------|------|
| 搜索缓存 | `app/services/search_service.py` | 缓存 Tavily / DDG 搜索结果，降低搜索成本和外部 API 压力 |
| Embedding 缓存 | `app/services/rag_service.py` | 对确定性的 embedding 结果做批量缓存，跨任务复用 |
| 热进度缓存 | `app/services/task_service.py` | 任务运行中的状态、进度、当前轮次写 Redis，便于跨进程实时查询 |
| 分布式限流 | `app/services/rate_limiter.py` | Redis Lua 令牌桶限制多 worker 下的全局 LLM 请求速率 |

缓存服务遵循“降级安全”原则：Redis 不可用时自动旁路，不阻断研究流程。

### 3.2 SQLite 的职责

SQLite 当前作为系统记录层（SoR）：

| 能力 | 代码位置 | 说明 |
|------|----------|------|
| 任务持久化 | `app/services/db.py` | `tasks` 表保存任务状态、查询、时间、完整 JSON |
| 任务服务 | `app/services/task_service.py` | 创建、更新、查询、列表、报告读取统一走 SQLite |
| 并发友好 | `app/services/db.py` | SQLite 开启 WAL、busy_timeout，支持单机多 worker 共享 |

SQLite 适合当前单机部署和开发阶段。若后续进入多机部署，可通过 `DATABASE_URL` 切到 MySQL / PostgreSQL，任务服务代码不需要大改。

### 3.3 队列与 worker

任务队列使用 arq：

- API 创建任务后优先入 Redis/arq 队列
- 独立 `arq app.worker.WorkerSettings` worker 进程消费任务
- 多个 worker 共享 Redis 队列，自动分摊任务
- 队列不可用时回退到 `asyncio.create_task` 进程内执行

这使 API 服务可以保持轻量，真正耗时的研究流程由 worker 池承担。

## 4. 当前技术栈状态

| 层级 | 当前技术 | 状态 |
|------|----------|------|
| API 服务 | FastAPI | 已稳定承担任务创建、状态查询、报告查询 |
| 工作流编排 | LangGraph | 核心流程已实现 |
| 后台任务 | arq + Redis | 刚接入，支持多 worker |
| 系统记录 | SQLite + SQLAlchemy async | 刚接入，支持持久任务列表 |
| 缓存 / 限流 | Redis | 刚接入，覆盖搜索、embedding、进度、LLM 限流 |
| RAG | Qdrant memory + bge-m3 + reranker + xling | 质量优化已有基准支撑 |
| 前端 | Streamlit | 适合验证，不适合产品化 |
| 部署 | 本地 Python + 可选 Redis compose | Docker 仅保留 Redis 服务 |

## 5. React / Node.js 扩展方向

### 5.1 React：建议优先引入

React 最适合解决当前项目的产品化 UI 问题。

适用场景：

- 任务创建页：输入研究问题、选择轮次、报告类型、语言、搜索深度
- 任务列表页：展示历史任务、状态、进度、耗时
- 任务详情页：实时进度、节点阶段、错误信息、最终报告
- 报告阅读页：Markdown 渲染、来源引用、导出、复制
- Benchmark / 运维页：缓存命中、worker 状态、任务吞吐、失败率

推荐方案：

```text
React + Vite + TypeScript
  -> 调用现有 FastAPI REST API
  -> 短期使用轮询 /api/research/{id}/status
  -> 中期增加 SSE 或 WebSocket 推送进度
```

优势：

- 不影响 Python 核心研究链路
- 可以替代 Streamlit，提升交互体验
- 前后端边界清晰，适合后续部署和权限系统
- 与当前 FastAPI API 形态匹配

### 5.2 Node.js：暂不建议进入核心后端

Node.js 可以考虑，但不建议马上引入到核心研究流程。

不建议替换的部分：

- LangGraph 工作流
- RAG / embedding / reranker
- 搜索抓取与信源评估
- LLM 调用与事实核查
- worker 执行链路

原因：

- 当前核心能力高度依赖 Python 生态
- Redis/SQLite/arq 已经解决主要并发瓶颈
- 再引入 Node 后端会增加部署、认证、日志、错误追踪、数据一致性复杂度

可以考虑的 Node.js 场景：

| 场景 | 是否建议 | 说明 |
|------|----------|------|
| React 构建工具链 | 建议 | Node 作为前端构建环境即可 |
| BFF 网关 | 可选 | 当 API 聚合、权限、SSE/WebSocket 复杂后再考虑 |
| 实时通知网关 | 可选 | 若 FastAPI SSE/WebSocket 不满足时再拆 |
| 核心任务执行 | 不建议 | Python worker 已承载核心流程 |
| RAG 服务迁移 | 不建议 | 当前 Python 模型和评测链路更成熟 |

## 6. 推荐路线

### 阶段 1：引入 React，保留 Python 单后端

目标：替换 Streamlit，形成可产品化 Web UI。

建议任务：

1. 新建 `web/` 前端目录
2. 使用 Vite + React + TypeScript
3. 封装 FastAPI 客户端
4. 实现任务创建、任务列表、任务详情、报告展示
5. 状态进度先使用轮询，避免过早引入实时通道复杂度

推荐边界：

```text
React Web
  -> FastAPI REST
    -> SQLite / Redis / arq / worker
      -> LangGraph / RAG / LLM
```

### 阶段 2：增加实时进度能力

目标：减少轮询压力，提升任务执行可见性。

优先方案：

- 在 FastAPI 增加 SSE：`GET /api/research/{task_id}/events`
- 后端从 Redis 热进度读取或使用 Redis pub/sub 推送

此阶段仍不需要 Node.js。

### 阶段 3：视复杂度决定是否引入 Node BFF

只有当出现以下需求时，再考虑 Node.js：

- 多前端客户端统一 API 聚合
- 复杂权限 / session / OAuth 编排
- 大量实时连接需要独立网关
- 前端需要服务端渲染或 Next.js 全栈能力

若进入该阶段，建议 Node.js 只做 BFF，不碰研究核心：

```text
React / Next.js
  -> Node BFF（认证、聚合、实时连接）
    -> FastAPI Research API
      -> Python worker 核心研究流程
```

## 7. 主要风险与注意点

1. Redis 目前是多职责组件：缓存、队列、热进度、限流都依赖 Redis。生产部署需要监控内存、淘汰策略、连接数和持久化策略。
2. SQLite 适合单机多 worker。多机部署前应切 MySQL / PostgreSQL。
3. Qdrant 当前仍是内存模式，研究任务内可用，但进程重启后向量索引会丢失；如果要做跨任务知识库，需要改为持久 Qdrant。
4. React 引入后，需要明确 API schema 和错误码，否则前端会被后端状态细节牵着走。
5. Node.js 不应为了“技术栈更完整”而引入。当前真正缺的是产品化前端和实时进度体验，不是第二套后端。

## 8. 结论

当前后端已经完成关键的高并发基础设施升级：Redis 负责队列、缓存、热进度和分布式限流，SQLite 负责任务持久化，arq worker 负责横向消费任务。这个阶段最值得扩展的是前端体验，而不是重写后端。

建议优先采用：

```text
React + TypeScript + Vite
```

作为新的 Web 前端，直接对接现有 FastAPI。

Node.js 暂时只作为前端构建环境存在；等出现复杂 BFF、认证聚合或大规模实时连接需求时，再评估是否引入 Node.js 服务层。
