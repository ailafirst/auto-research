# 检索路由蓝图：从 AnySearch 调研到 P0 实测修正

> 记录 `retriever_node` 检索路由这条线从「读 AnySearch 调研」到「P0 落地、跑偏、修正、最终确认」的完整过程，以及对比 AnySearch 后暴露出的不足和后续优先级。承接 [AnySearch技术原理与项目借鉴调研.md](AnySearch技术原理与项目借鉴调研.md)，补充材料在 [检索与证据.md](检索与证据.md)。

## 0. 结论先行

P0（域驱动路由 + 结果来源元数据）已落地，**真实收益是 12 题基准集总耗时 -7.4%，且集中在 business/legal/policy 三个域**——不是最初汇报的 -50%。中间有一版因为方法论缺陷把节省数字做虚高了，本篇也如实记下这段弯路，不只记结果。

对比 AnySearch，当前系统的核心差距不是"路由算法不够聪明"，而是**只有一个垂直源（学术白名单）可路由**：business/legal/policy 域收益为零的根因是压根没有对应的垂直检索源，不是路由逻辑判断错了。**重心调整为补这个缺口（§5 的 #1）**，路由粒度、跨源融合排序、结构化子域参数这三项差距（§5 的 #2-#4）保留为已知问题。

**#1 现已推进一版**（§7）：不接外部 AnySearch（需要账号/API key/DPA 审核，本地没有凭据也无法代为采购），而是仿照学术白名单的路数，在项目内给 business/legal/policy 各建一份权威域名白名单，接入既有的域驱动路由框架。上线前用与 §3/§4 同一方法论（真实 Tavily 请求测 `tavily_score >= 0.5` 命中率，而非只看请求数）验证了三个域确有 33%~40% 的真实证据命中率，量级与当年为 technology 域打开学术路由时的证据（~40%）相当，不是自证。顺带测了唯一还没覆盖的 `education` 域（Planner 的 7 个 domain 枚举里，5 个已有垂直路由），命中率 25% 且分布很不均匀，判定不达标暂不接入（§7.5）。这一步单独看代价是 12 题基准总耗时从 932.3s 涨到 1078.1s（+15.6%）。

**#2 紧接着也推进了一版**（§9）：最初的假设——让 Planner 给每个子问题多标一个"研究/机制类 vs 应用/实践类"字段（`evidence_lens`）——**被真实数据证伪**（两组命中率都是 53%，毫无区分度），已回退。复核同一份数据时找到真正的信号：**查询语言**——英文查询打学术白名单命中率 92%，中文查询只有 9%，跟问题是研究型还是实践型无关，是 arxiv/IEEE 这类纯英文语料库结构性决定的。据此加了一个纯代码层面的语言门控（不改 Planner），跳过中文查询对 academic 路由的白费请求，把 §7 新增三域后涨到 1078.1s 的总耗时压到 **922.4s**。

**但"跳过中文"只是止损，不是终点**——项目最终面向中文母语用户，§9.5 复核发现 legal/policy/business/education 的低命中率根本不是"中文语言劣势"，是白名单选的清一色西方机构，中文查询自然搜不到对应答案。换成中国官方一手源（gov.cn/npc.gov.cn/ndrc.gov.cn/moe.gov.cn 等）重测同一批中文查询：legal/policy/education 命中率跳到 **100%**，business 到 50%，全面超过之前打西方白名单的 33%~40%。这才是真正解决问题，而不是绕开问题——已把这四个域从"跳过"改成"换源"，改完后 12 题基准总耗时 **886.8s**，因为是换白名单不是加请求，成本不变，纯收益。

**规模审计 + 扩到 10 个垂直域**（§9.6-9.7）：中英文白名单不能只看"有没有"，还要看"够不够"——逐路由清点域名数后发现 `academic` 中文侧完全空白、`education` 中文侧只有 1 个域（单点故障）。`academic` 换个思路（找中国官方科研机构的研究通报而非"中文版论文"）后测出 80% 命中率，`education` 补到 3 个域后仍 93%。同时对照 AnySearch 差距清单，把此前缺失的 health/code/ip/security 四个域补上（`code`/`security` 中文侧未测/不达标，如实标注为跳过而非硬凑），垂直路由总数从 6 个扩到 **10 个**，同步把 Planner 的 domain 枚举从 7 个扩到 11 个并验证分类准确（新域 6/6 分类正确，原有域无回归）。这四个新域目前没有对应的端到端基准任务，留作后续观察项。

**"每个语言侧都要独立成规模"（§9.8-9.9）**：用户提出更高标准——中英文白名单不该只是"有"，各自都该有约 10 个域名的规模。补候选重测后 legal/policy/education/business/health 各有实质提升（+2~+3），code/security 补出合格中文源后正式从"跳过"策略转为"换源"策略，但没有一个路由真正摸到 10 个，`academic` 这轮补测甚至颗粒无收（候选测了个遍，命中率最高只有 29%）——中文权威源的可检索规模本身就是硬约束，不是白名单没选对就一定能凑出来的。`ip` 域尤其明显：候选池测到见底（业内最大的行业媒体 `cnipr.com` 反而命中率最低，仅 13%），最多凑到 3 个，用户据此决定放弃扩容、直接**换成 `environment`（环境）**——参照 AnySearch 领域清单，EN/ZH 双侧首轮实测均 100%，同时把 `app/prompts/planner.md` 的 domain 定义和边界区分说明一并替换，验证分类无回归。

**规模补齐到 10/10 + 回头验证意图识别（§9.10-9.11）**：用户明确要求这一轮暂停命中率验证，先把 10 个域的中英文白名单都补够 10 个（官方源优先，见底后补认可度高的百科/论坛/社区），如实标注这批未经实测，与此前实测过的条目区分开。补齐后回头用真实 Planner 调用测了两轮意图识别准确率：首轮 35 条测出 97.1%，用户质疑样本太小太集中，扩到 92 条（每域 5 条清晰案例跨子领域分散 + 32 条边界案例 + 5 条英文）重测，**准确率修正为 90.2%（83/92）**，发现三个可复现的系统性模式而非偶然误判：`code` vs `technology` 在基础设施配置类问题（K8s/PostgreSQL/SQL 报错）上 3/3 系统性判错；`environment` vs `policy` 在政策学措辞包裹环境议题时 2/2 倒向 `policy`；`general` 域近乎不可达，5 条刻意设计的无主导视角问题只有 2 条被认可，其余被 LLM 强行找出主导视角归类。详见 §9.11-9.12。

**根因诊断 + 修复（§9.13，已实现）**：三个模式共享同一个架构根因——`domain` 曾是**整个研究计划级别**的单一全局标签，`retriever_node` 用它决定所有子问题是否走垂直路由。已把 domain 判断下沉到**子问题级别**：Planner 给每个 sub_question 单独标 domain（保留顶层 domain 供 report_writer/analyst 做全篇框架用），retriever 按子问题查路由表，第 1 轮和第 2+ 轮补证（`_supplement_round`）共用同一套路由逻辑。四层验证（mock 单测、真实 Planner 混合域测试、单域回归、真实 `run_research()` 闭包链路集成测试）均通过。

**AnySearch 差距 #2 增量（§9.14，已实现）**：§9.13 只做到"决策粒度下沉到子问题"，AnySearch 原则②"不确定时混合，不是二选一"还没有对应实现——边界子问题猜错一个 domain 就完全错过另一个域的垂直源。新增 `domain_secondary` 字段（Planner，仅真正跨域时标注）+ `search_vertical_multi`（两个域的垂直路都搜，按 URL 去重合并），多数单域子问题不受影响。单测和真实 Planner 调用验证机制本身正确、无误触发；但对 §9.12 两个已知边界模式的改善不对称——`environment`/`policy` 测出 1 次真实生效，`code`/`technology` 这批样本 0 次触发，如实记录，留作后续观察。

**AnySearch 差距 #3 + #4（§9.15，已实现）**：跨源融合排序 + 结构化子域参数契约。真实请求对比 Semantic Scholar 和 CrossRef 两个免费学术 API——Semantic Scholar 匿名池持续 429（需申请 key），CrossRef 稳定可用，选定后者绑定 academic 路由，返回 DOI/被引数/期刊/年份等结构化字段。同时实现 `_fuse_and_rank()`：通用路/垂直路/结构化路结果按 authority/diversity/freshness 可解释融合评分排序，取代原来的"通用优先、URL 去重先到先得"拼接。过程中真实数据测出一个 bug 并修复：CrossRef 结果 URL 统一是 `doi.org`，diversity 分组若按域名算会把不同期刊的论文误判成同一来源，全部拖累排名，改用 DOI 出版社前缀分组后修复。已知局限如实记录：CrossRef 全文检索对小众技术话题匹配偏松、融合权重是经验默认值未做数据集调优、结构化数据源目前只覆盖 academic 一个路由。

**补第二个结构化数据源：arXiv（§9.16，已实现）**：CrossRef 只索引正式发表带 DOI 的文献，对 vLLM PagedAttention 这类先挂预印本、后（甚至永远不）正式发表的前沿系统研究天然滞后——这正是 §9.15 记的"CrossRef 匹配偏松"局限的根因之一。接入 arXiv 官方 API 作为补充（不是替代），`STRUCTURED_ROUTE_PROVIDERS` 从"一个路由一个数据源"改成"一个路由多个数据源"的列表结构，academic 路由现在并发查 CrossRef + arXiv。过程中真实测出两个问题：arXiv API 官方给的 `http` 地址已强制跳转 `https`，httpx 默认不跟随导致请求静默失败；查询词强制 `AND` 连接在 4 词以上的长查询上过严，实测直接 0 命中，改为"精确 AND 匹配 0 条时自动降级为宽松匹配"的两级策略。

**跨 provider 去重：规范标识符优先于 URL（§9.17，已实现）**：接上条局限——同一篇论文经 Tavily 爬到的页面和 CrossRef/arXiv API 返回的规范 URL 因形式不同不会被去重。查了 AnySearch 怎么做，去重规则明确属于未公开信息，查不到；转向业界公认做法（OpenAlex/Semantic Scholar/文献管理软件的通用做法）：去重键从原始 URL 换成"DOI/arXiv ID 优先、都没有才退回 URL"的规范标识符，命中同一标识符时保留结构化信号最丰富的版本而不是先到先得。过程中真实数据又测出一个 bug：arXiv ID 正则最初只认 `arxiv.org/abs/` 和 `arxiv.org/pdf/`，漏了 Tavily 实际爬到的 `ar5iv.labs.arxiv.org/html/`（arXiv Labs 官方 HTML 渲染镜像），修复后 vLLM PagedAttention 查询里同一篇论文的重复实例从 3 条正确合并为 1 条。已知局限：只有 URL 里真的嵌了 DOI/arXiv ID 才能合并（Nature 这类用自有短 ID scheme 的出版商页面合并不了，已用真实 URL 形态验证这个边界）；未做标题模糊匹配兜底，按用户决定留到看完这版效果再定。

**全量 12 题基准验证（§9.18，已完成）**：把 §9.15-§9.17 三项改动放到项目真正的基准负载（12 题全集，并发 2）下一起验证，前几轮都只测了单条查询规模，没测过真实并发。结果：12/12 任务全部成功、子问题全覆盖、无崩溃，降级安全按预期工作；但真实测出 CrossRef/arXiv 这两个免费匿名 API 在这个并发量级下会被限速——CrossRef 43 次请求里 41 次 429，arXiv 68 次请求**全部** 429，单条查询测试完全测不出这个问题。12 题总耗时从改动前的 886.8s 涨到 1291.8s（+45.7%），代价是新增网络请求量本身（即使 429 失败也要付网络往返时间），不是路由逻辑变慢。已知局限如实记录：目前对结构化源请求失败没有任何重试/限速处理（不重试本身没有引发级联问题，但意味着 academic-structured 命中数会随时段限速状况波动，不是稳定可复现的数字）；是否需要给这两个数据源单独加一层更保守的并发控制来换回耗时，本轮不做，留待决策。

**给 CrossRef/arXiv 各设进程级并发上限（§9.19，已实现）**：承接 §9.18 留的决策项，先落地代价最小的一步——`llm_service.py` 同款的进程级 `asyncio.Semaphore` 模式，两个源各设一个并发上限（`arxiv_max_concurrency=2` 比 `crossref_max_concurrency=3` 更保守，依据是 arXiv 官方使用须知明确要求"不超过每 3 秒 1 个请求"，是三个源里唯一有书面速率条款的）。这一步压的是"同一时刻并发在飞的请求数"，不是总请求量，也不是严格的时间间隔限速——如实标注对滑动时间窗口式限速可能仍不完全免疫。用 mock 请求 + 计数锁验证信号量本身按配置精确生效（CrossRef 峰值=3、arXiv 峰值=2），未重跑真实网络规模的 429 对比实验。

**重跑 12 题基准验证效果（§9.20，已完成）**：补上 §9.19 没做的真实负载对比，与 §9.18 同规模重跑。**结果是分化的**：CrossRef 请求失败从 43 次压到 2 次，改动明显生效；但 arXiv 请求失败仍有 74 次、全部 429，跟改动前的 68 次相比没有观察到任何改善，印证了 §9.19 的推测——`asyncio.Semaphore` 限的是并发数，不是请求间隔，管不住 arXiv 按时间窗口算的限速。总耗时 1303.4s，和改动前的 1291.8s 基本持平，没拿回之前的耗时代价。**不能汇报为"并发限流解决了限速问题"**——只对 CrossRef 有效，arXiv 侧要解决大概率需要换成按时间间隔控制的限速器（如令牌桶），本轮不做，留待决策。

**诊断 arXiv 无效的真实成因（§9.21，已完成）**：绕开业务代码，用最原始的 httpx 请求分四轮直击 arXiv 官方 API，逐步排除假说——单发/间隔递增发送、真并发 2/3/5 个、零间隔连发 10 个、"并发=2"节流 6 秒内打 40 个，全部 200，没有一次 429，证明"并发数""零间隔连发少量请求"都不是触发条件。直到用"并发=2"节流持续打 120 个请求才复现：**前 20 个（约 7 秒内送出）全部成功，第 21 个起转为持续 429**。**根因确认：arXiv 限的是短时间窗口内的累计请求数（约 20 个/7 秒量级），不是同一时刻并发数**——并发=2 时吞吐仍能跑到每秒 3~6 个，几秒内照样能把配额打穿，`arxiv_max_concurrency` 从设计动机上就没对准真正的触发条件，这就是 §9.20 测出"无改善"的直接原因。撞线后探测恢复时间，累计约 298 秒（约 5 分钟）后恢复 200（受当天反复测试干扰，不是一次干净独立测量，但确认冷却期是分钟级而非秒级）。要真正解决需要换成请求速率限制器（固定间隔/令牌桶），不是继续调并发数，本轮只诊断不改代码，留待决策。

**给两个源都接上跨进程速率限制器（§9.22，已实现）**：用户要求 CrossRef 和 arXiv 一起做，且"彻底避免问题"。动手前先补测了 CrossRef 的真实阈值（此前只有生产负载下的结果）：瞬时并发 ≤8 稳定成功，12 个起零星失败，20 个近半失败——确认 CrossRef 是"瞬时并发连接数"型限速，跟 arXiv 的"时间窗口累计请求数"型本质不同，现有 `crossref_max_concurrency=3` 本地信号量已在安全范围，真正的缺口是**本地信号量只在单进程生效，多 worker 部署下聚合并发是 N 倍，两个源都一样防不住**。实现上复用项目里已有的 `RedisRateLimiter`（`app/services/rate_limiter.py`），跟 `llm_service.py` 给 LLM 调用做跨进程限速同一套机制——本地信号量之前先过一道 Redis 令牌桶，Redis 不可用时直接放行、本地信号量兜底。arXiv 侧速率对齐官方"不超过每 3 秒 1 个请求"（0.33/s，不留突发余量），且把 `RedisRateLimiter.acquire()` 默认 30s 的排队超时拉长到 120s——按默认值算，一个 deep 任务同时冒出十几个 academic 查询很容易排队超过 30s，超时后会放弃排队直接放行，反而制造新的突发，正好撞回根因。CrossRef 侧速率对齐已验证有效的本地并发上限（3/s）。**真实网络 + 真实 Redis 验证**：复刻此前打崩两个源的并发场景（15 个 arXiv 查询同时发起、20 个 CrossRef 查询同时发起）——**两边全部成功，0 个失败，日志里没有一条 429**。代价如实记录：arXiv 侧节流后 15 个查询耗时 65.0s（用等待时间换稳定性），CrossRef 侧几乎无感（7.0s）。未做的验证：多 worker 场景下的联合测试、重新完整跑一次 12 题基准做端到端总耗时对比（arXiv 节流对单任务总耗时的影响需要专门测）。

**补上完整 12 题基准端到端验证（§9.23，已完成）**：CrossRef 请求失败**降到 0 次**（§9.18 的 43 次、§9.20 的 2 次），彻底清零；总耗时 **973.1s**，比 §9.20 的 1303.4s 少 25.3%，离两个新数据源接入前的原始基线 886.8s 只差 86 秒。arXiv 仍有 32 次失败，全部集中在整个 973 秒运行最初的一小段（日志前 71 行），当时推测是当天反复诊断测试遗留的冷却期尾巴，建议找干净窗口重新验证——**这个推测在 §9.24 被推翻**。

**干净起点压力测试复核，修正 §9.23 的乐观结论（§9.24，已完成）**：先单发探测确认 arXiv 处于干净状态（200），再跑一次同规模基准。结果 arXiv 失败**反而更多**（67 次），且**不再集中在开局**，而是散布在运行的大部分时间段，抽样连续失败区段里完全没有成功请求穿插。逐项核对排除了限流器本身失灵——配置值正确、全程 0 次"放弃排队"记录，**每次请求都严格遵守了 ≥3 秒间隔才发出**。**修正后的结论**：arXiv 一旦进入拒绝状态，接下来一段时间（量级同 §9.21 测出的约 5 分钟冷却期）会无差别拒绝，不因为后续请求发得更克制而提前恢复；纯靠调小客户端发送节奏这一个维度无法彻底根治，问题可能已经触达服务端全局负载或更长周期配额这类客户端手段覆盖不到的层面。好消息是**这不影响任务正确性**：12 个任务依然全部全覆盖，CrossRef 继续 0 失败并顶上更多命中（academic-structured 580 条，仍健康）。"彻底避免问题"这个目标需要诚实修正为"降低发生概率、不主动恶化、继续依赖优雅降级兜底"——已实现的方案仍值得保留，但不等于零 429 的承诺。

**分速率压力测试找平衡点（§9.25，已完成）**：单流严格串行分别测 0.15/0.33/0.6 三档速率——0.15/s 和 0.33/s（现值）连发 24 个全部成功，0.6/s 从第 20 个开始失败（约 20 个/33 秒触发，跟 §9.21 的"约 20 个/7 秒"是同一个短窗口配额，只是换速率把触发时间推后了）。**确认现有 0.33/s 设置本身在安全区间，不需要调更保守**。进一步排查 §9.24 那 67 次失败是不是"生产代码允许并发=2"导致的：干净起点下用生产同款"并发=2、整体节奏 0.33/s"发 40 个，**全部成功**——推翻了"并发=2 是罪魁祸首"的猜测，现有配置组合本身没问题。同时意外发现一个更关键的现象：手动探测确认干净后，中间没有对 arXiv 发过任何请求，隔几分钟脚本自己再探测又变回 429——说明是否处于受限状态不完全由我们自己的请求行为决定，可能跟服务端全局负载或比单次冷却期更长的信誉/配额机制有关，这部分已经不是客户端调参能控制的了。附带验证了"一旦真进入冷却期，拼节奏没用"——单流串行 0.33/s 连续 80 个请求、持续 240 秒全部规规矩矩排队，因为起跑时已在冷却期内，**80/80 全部失败，无一例外**。据此提出一个待决策的新思路：加一层熔断——收到第一次 429 后，接下来几分钟内 academic 域查询直接跳过 arXiv 只用 CrossRef，省下注定失败的排队等待成本，本轮只提出不实现。

**落地熔断并验证（§9.26，已完成）**：参数不动（§9.25 已验证现有组合安全），只加熔断——第一次收到 429 后 360 秒内直接跳过 arXiv、不再发真实请求，mock 单测验证熔断触发/跳过/恢复三段行为均符合预期。真实 12 题基准复核：arXiv 429 次数从 §9.24 的 67 次降到 **6 次**（本轮只真正撞进一次冷却状态，命中后再没出现新的 429），总耗时 540.4s，比 §9.24 的 616.1s 再收窄 12.4%，是目前耗时最短的一轮，12/12 任务全覆盖不受影响。如实记录一个意外现象：CrossRef 本节代码未改动，却首次在完整基准里观察到 6 次分散的 429（此前两轮均为 0），样本量不足以下结论，留作后续观察项。熔断解决的是"命中冷却后别再送死"，不改变"是否会被判定进入冷却"这件事本身受客户端不完全控制的现实——这部分留给后续如需要再考虑申请官方 API key。

## 3. 复核：验证方法本身测不出真正的风险

用户追问"AnySearch 在 P0 上的效果，是否我们搞错了什么"，倒逼回头检查两处：

1. **`retriever_benchmark.py` 只调 `planner_node` + `retriever_node`，不经过 `source_evaluator_node`。** raw_content% 和子问题覆盖率这两个"质量代理指标"只能证明"有结果"，证明不了"丢掉的结果是不是本来会被采纳"。之前拿这两个指标当"零质量回退"的证据，是把检索层的指标当成了证据层的结论。
2. **`ACADEMIC_ROUTE_DOMAINS = {"science"}` 这个收窄本身没有实测支撑**，只是"学术白名单只对 science 有意义"这个直觉。

直接用真实 Tavily 请求测了几个案例，看学术路结果的 `tavily_score` 能不能过 `source_evaluator` 的采纳阈值（`>= 0.5`）：

| 查询 | domain | 学术路命中率（PASS/总数）|
|---|---|---|
| LLM推理加速（vLLM/PagedAttention） | technology | 2/5（0.79、0.61）|
| LLM幻觉成因机制 | technology | 2/5（0.79、0.54）|
| 微服务 vs 单体架构 | technology | 0/5 |
| 电商推荐系统冷启动 | technology | 0/5 |
| 英伟达AI芯片竞争格局 | business | 0/5 |
| GDPR执法力度 | legal | 0/10（general+academic都试了）|

本项目 Planner 把"LLM推理加速""LLM幻觉问题""AGI技术障碍"这类 AI/ML **研究型**问题分类成 `technology`，不是 `science`。`ACADEMIC_ROUTE_DOMAINS = {"science"}` 把这些问题的真实相关证据（真命中的 arxiv 论文）静默切掉了，而 §2.3 的验证方法从设计上就看不到这个损失。

同时也确认了 business/legal 域、以及 technology 域内纯工程实践问题（微服务选型、推荐系统冷启动）的学术路命中率确实是 0——收窄这部分是有数据支撑的。

## 5. 对比 AnySearch：现在还差什么

这次基准结果说明的不是"路由算法还不够聪明"，而是**候选池里压根没有能路由到的垂直源**——05/06/07（business/legal/policy）三个任务无论路由逻辑怎么调，收益都是 0，因为唯一的垂直源（学术白名单）对这三个域天然不匹配。对比 AnySearch 报告列出的能力，差距排序如下，**#1 是当前重心，#2-#4 保留为已知问题**：

| # | 差距 | 现状 | AnySearch 对照 | 优先级 |
|---|---|---|---|---|
| **1** | **垂直源数量** | 10 个（science/technology 共用 academic，另 business/legal/policy/education/health/code/environment/security，覆盖 11 个 domain 枚举中的 10 个，见 §7、§9.7、§9.9） | 17 个域（finance/legal/health/code/ip/security…） | **进行中**——finance/legal/health/code/security 缺口已补齐；`ip` 因中文候选池见底换成了 `environment`；中英文各侧的域名规模仍未达到用户要求的约 10 个/路由（见 §9.8），仍差约 7 个未知具体域名的域 |
| **2** | **路由粒度** | 已下沉到子问题级（§9.13），边界/不确定子问题支持双域混合检索而非强制二选一（`domain_secondary` + `search_vertical_multi`，见 §9.14） | 查询/子域级，`get_sub_domains` + 结构化参数 | **决策粒度和"不确定时混合"两条已落地**——`sub_domain_params` 那层结构化参数由 #4 落地 |
| 3 | 跨源融合排序 | **已实现**（§9.15）：通用路/垂直路/结构化路结果按 authority/diversity/freshness 可解释融合评分排序，取代原来的"通用优先、URL 去重先到先得" | 声称按 authority/diversity/freshness 做 fusion ranking（公式未公开） | **已实现**，权重是本项目定的经验值，未做过标注数据集调优 |
| 4 | 结构化子域参数契约 | **已实现 1 个路由、2 个数据源**（§9.15/§9.16）：academic 路由接入 CrossRef + arXiv 两个 API，互补返回 DOI/被引数/期刊/年份/预印本分类等结构化字段，其余 9 个路由仍是自由文本 query + domain 字符串，无对应结构化数据源 | `sub_domain_params`（如 `finance.quote` + `symbol=AAPL`） | 覆盖面仍窄（1/10 路由），其余域要补齐需要各自找到可用的免费结构化数据源，不是代码模式可以直接复制 |

**#2 的具体证据与结论**：v2 时 technology 域内部确实有浪费——"LLM推理加速"这类研究型问题命中率 ~40%，"微服务架构选型"这类工程实践问题命中率看起来 ~0%。最初设想用 Planner 已产出的 `dimensions`/`intent` 做二级过滤，但真正尝试后发现两个问题：(a) 这两个字段是任务级的，不是逐子问题的，本身就不能做子问题级过滤；(b) 专门为此新增的子问题级字段 `evidence_lens`（研究/机制类 vs 应用实践类）经实测证明和命中率没有任何相关性（53% vs 53%）。真正找到的信号是查询语言（92% vs 9%，见 §9.2），且与"研究型 vs 工程型"这个最初的直觉无关——连"微服务选型""电商推荐系统冷启动"这类此前判定为~0%命中的工程问题，换成 Planner 实际生成的英文查询后命中率同样能到 90%+。也就是说 §3 当时"某些工程类问题学术路命中率≈0%"的结论本身有方法论局限（手写单句中文查询，非生产实际查询集），不是这些问题真的没有可用的学术证据。

**#1 为什么是重心**：business/legal/policy 域收益为零，不是本项目路由判断的问题，是结构性的——想让这三个域从"检索"里获得增益，唯一路径是**要么给它们建对应的垂直源，要么真的去接一个已经做了这件事的服务**（AnySearch 或同类）。这正是 AnySearch 调研报告 §9 里 P1（"为 AnySearch 设计可选 Provider 的小型适配 POC"）的适用场景，但执行时仍要遵守报告 §7.3 的方法论：不能只看请求数/覆盖率这类检索层指标（§3 的教训），要接到 `source_evaluator`/RAG 之后测真实证据采纳率，且优先在 business/legal/finance 这类当前完全没有覆盖能力的域上做受控对比，而不是扩大到已经验证过的 science/technology。

## 7. 差距 #1 v1：自建垂直源（不接 AnySearch）

### 7.1 为什么不直接接 AnySearch

调研报告 §7/§8 把 AnySearch 定位为需要账号/API key 的第三方服务，接入前要走数据处理地域、DPA、配额、法务/采购审核——这些是需要人决定并去申请的事，不是代码改动能替代的。相比之下，在项目内自建垂直源只是"给 `search_academic_dual` 已经验证过的路数换一份域名白名单"，不新增供应商依赖，可以直接用 §3/§4 已经验证过的方法论继续做。两条路不冲突，AnySearch POC（调研报告 P1）仍保留在 backlog，取决于是否决定采购。

### 7.2 实现

- `app/services/search_service.py`：新增 `BUSINESS_ALLOWLIST`（sec.gov / worldbank.org / imf.org / oecd.org / bloomberg.com 等 15 域）、`LEGAL_ALLOWLIST`（eur-lex.europa.eu / law.cornell.edu / courtlistener.com / wipo.int 等 13 域）、`POLICY_ALLOWLIST`（oecd.org / iea.org / un.org / brookings.edu 等 13 域）。域名选取原则是"一手信源优先于媒体转述"：监管/立法机构、国际组织、判例库，而非新闻网站首页——后者命中率高但多为二手转述，本身在 general 路里已经能搜到，垂直路的增量价值在于 general 路搜不到的一手文献。
- 原来的 `ACADEMIC_ROUTE_DOMAINS: frozenset[str]`（只能标记"命中/不命中"）泛化成 `VERTICAL_ROUTES: dict[str, tuple[str, list[str]]]`（domain → (路由名, 白名单)），science/technology 沿用已实测确认的学术白名单，business/legal/policy 指向新增的三份白名单。
- `search_academic_dual()` 泛化为 `search_vertical_dual(query, route_name, allowlist, max_results)`，逻辑不变（通用一路 + 白名单一路并发合并，按 URL 去重），只是白名单和路由名从硬编码改成参数。
- `app/graph/nodes.py::retriever_node`：`domain in ACADEMIC_ROUTE_DOMAINS` 布尔判断改成 `VERTICAL_ROUTES.get(domain)` 查表，命中即触发对应垂直双路。
- `settings.academic_search_enabled` 保留原名（历史遗留，不改环境变量名避免破坏已部署配置），但语义扩大为"全部垂直路由的总开关"，注释同步更新。

### 7.3 上线前验证：不重复 §3 的方法论错误

新白名单"看起来权威"不代表真的有命中——§3 的教训是只看请求数/覆盖率会掩盖零命中的白费请求。上线前直接用真实 Tavily 请求测了 business/legal/policy 各 3 组代表性查询（对应基准任务 05/06/07 的实际研究方向）的 `tavily_score` 命中率：

| 域 | 命中率（PASS/总数，`tavily_score >= 0.5`） | 典型 PASS 来源 |
|---|---|---|
| business | 5/15（33%） | imf.org、wsj.com |
| legal | 5/15（33%） | gdpr-info.eu（GDPR 原文逐条款） |
| policy | 6/15（40%） | worldbank.org、imf.org |

三个域的命中率与当年为 technology 域打开学术路由时的证据（~40%，见 §3）量级相当，明显高于 §3 里验证过的"business/legal 走*学术*白名单"的 0% ——说明问题不在这两个域本身没有可用一手证据，而在于之前唯一的白名单（学术）本来就选错了域名池。这份证据支持把三份新白名单接入路由，而不是重复"域名列表看起来权威就直接上线"的假设性判断。

### 7.5 顺带测了 education 域：一开始判定不达标（后被 §9.4 推翻）

Planner 的 domain 枚举实际只有 7 个（`technology/business/science/legal/education/policy/general`），不是无限对标 AnySearch 的 17 个域——按自己的分类体系算，5/7 已有垂直路由，真正空着的只有 `education`。用同一方法论测了一版候选白名单（eric.ed.gov / unesco.org / nces.ed.gov / oecd.org 等）：4 类代表性查询里 3 类命中率 0/5，只有"PISA/国际教育水平比较"这类统计对比型命中 5/5，整体 25%（5/20），当时判定不达标，暂不接入。

## 9. 差距 #2：一个假设证伪，一个更强的真实信号

### 9.1 最初假设：子问题级"研究 vs 实践"分类（`evidence_lens`）——证伪

§5 的 #2 猜测是：`technology` 域内部命中率分裂（研究型 ~40%、工程实践型 ~0%，见 §3），根因是 domain 粒度太粗，需要更细的信号。最直接的想法是让 Planner 在每个子问题上多标一个字段，标注这个子问题的回答是否需要"机制/原理类"一手证据。

**实现**：在 `app/prompts/planner.md` 给每个 `sub_question` 加了 `evidence_lens: "mechanism" | "applied"` 字段（机制/原理类 vs 应用/实践类），并写了判断标准和跨域例子。

**验证**：没有直接上线，先用真实 Planner 调用 + 真实 Tavily 请求测了 3 个 technology 域任务（LLM 推理加速、电商推荐系统搭建、微服务 vs 单体架构）的全部子问题，按 `evidence_lens` 分组统计 `tavily_score >= 0.5` 命中率：

| evidence_lens | 命中率 |
|---|---|
| mechanism | 16/30（53%） |
| applied | 35/66（53%） |

**两组完全没有区分度**——`evidence_lens` 不能预测命中率，这个假设是错的。已把该字段从 `planner.md` 回退，不引入无意义的 schema 复杂度和 token 成本。

### 9.2 真实信号：查询语言

复核同一份验证数据时发现规律：几乎每条命中/不命中都和**查询语言**强相关，与 `evidence_lens`、与子问题是"研究"还是"实践"都无关。按查询语言重新分组（中文字符数 > 英文字母数 记为中文查询）：

| 查询语言 | 命中率（对 `ACADEMIC_ALLOWLIST`） |
|---|---|
| 英文为主 | 47/51（**92%**） |
| 中文为主 | 4/45（**9%**） |

机制上完全说得通：`ACADEMIC_ALLOWLIST` 里的 arxiv / IEEE / ACM / Nature / Science 等本身就是纯英文语料库，中文查询在这类源上天然吃亏，跟问题是不是研究型无关——甚至连"电商推荐系统冷启动""微服务 vs 单体架构"这类此前被判定为工程实践、学术路命中率约等于 0 的任务，只要用 Planner 实际生成的**英文**查询变体去测（而不是 §3 那种手写的单句中文摘要查询），命中率同样能到 90%+（如 `recommendation system cold start problem solutions` 命中 3/3，`monolith vs microservices architectural differences` 命中 3/3）。这也说明 §3 当时"某些工程类问题学术路命中率 ≈0%"的结论本身是被验证方法的查询颗粒度带偏的——用的是自己手写的单句概括查询，不是生产环境实际会发出的、按 Planner prompt 规则中英混合的查询集，该结论对"任务整体"成立，但不能证明"该任务下所有查询都零命中"。

**实现**：不需要改 Planner 的 prompt/schema（`evidence_lens` 已回退），纯代码层面加一个语言门控：

```python
LANGUAGE_GATED_ROUTES: frozenset[str] = frozenset({"academic", "education"})
```

`search_vertical_dual()` 里，`route_name` 命中该集合且 query 中文字符占多数时，直接跳过垂直路请求（只走通用路），省一次基本白费的 Tavily 请求。当时只对 `academic` 生效（`education` 是 §9.4 复核 education 域时一并加入的）：business/legal/policy 的白名单里有部分中文页面（`cn.wsj.com`、worldbank.org/imf.org 的 zh 文档），且 §7.3 测过的 business/legal/policy 命中率本身就是用中文查询测出来的（33%~40%，明显高于学术路中文查询的 9%）——这两件事放在一起说明"中文查询命中率低"不是普适规律，是纯英文语料池特有的现象，套到其他域之前必须单独验证，不能因为"看起来同理"就扩大范围。

### 9.3 端到端确认：12 题基准

| 指标 | v3（§7.4，含 business/legal/policy，无语言门控） | v4（本轮，加语言门控） |
|---|---|---|
| 总耗时 | 1078.1s | **922.4s（-14.4%）** |
| 相对 v2（§4.2，无 business/legal/policy 时的基线） | +15.6% | **-1.1%**（新增三域覆盖，总时间反而略低于加垂直源之前） |
| raw_content% / 子问题覆盖 | 96-100% / 12/12 | 94-100% / 12/12 |

语言门控只砍掉了 academic 路由里大概率白费的中文请求，science/technology 各任务仍能拿到几十条 academic 路结果（非零），业务侧行为不变；三个新域（business/legal/policy）不受影响，因为门控只对 `academic` 生效。数据存档：`benchmark/results/retriever_20260817_231250.json`。

**这一版的取舍**：92%/9% 是用 3 个 technology 域任务、32 条真实查询测出来的，样本不算大；`science` 域是否有同样效应目前是顺带验证（任务 03 academic 路结果仍非零），没有单独拆开测。business/legal/policy 的语言门控留空，是明确的未验证状态，不是"暂时忘了做"——扩大前需要同样一轮真实请求实测，不能凭"英文语料池都这样"的直觉套用。

### 9.4 两个追加问题：中文查询能不能救、education 域重新复核

用户追问两件事：中文命中率低有没有改进空间；§7.5 判定不达标的 education 域是不是也该用同样的语言视角重新看一遍。

**中文查询低命中率——暂不需要额外动作**。抽查了 3 个真实任务共 12 个子问题的 Planner 输出（只调用 `planner_node`，不消耗 Tavily 配额），统计每个子问题 `search_queries` 里的语言构成：**0/12 是全中文**，每个子问题都至少带 1 条英文查询（通常 3~4 条里有 1 条）。现有实现是按单条 query 字符串门控，不是按子问题门控，所以只要子问题里有英文变体，该变体仍会正常命中垂直路——目前没有证据显示存在覆盖损失，不需要加翻译或改 Planner 提示词来"抢救"中文查询。唯一的风险是"某个子问题恰好一条英文查询都没生成"，这次抽样没遇到，但样本只有 12 个，不是穷尽性证明，后续如果观察到反例再处理。

**education 域：§7.5 的"不达标"判断是被同一个语言盲点带偏的**。之前测 education 只用了中文查询（复用了 business/legal/policy 那套中文验证脚本，但没意识到 education 白名单和 business/legal/policy 不同——是纯英文机构源，跟 academic 更像）。用之前失败的 3 组问题（"如何学习机器学习""编程入门常见误区""MOOC学习效果"）换成英文重测，同时对比打 `EDUCATION_ALLOWLIST` 和直接复用 `ACADEMIC_ALLOWLIST` 两种选择：

| 白名单 | 命中率（英文查询） |
|---|---|
| `EDUCATION_ALLOWLIST`（eric.ed.gov 等教育研究专属源） | **11/15（73%）** |
| 直接复用 `ACADEMIC_ALLOWLIST` | 7/15（47%） |

三个原先 0/5 的问题分别变成 1/5、5/5、5/5。结论：25% 的低命中率主要是语言不匹配的假象，不是"education 没有一手信源"，也不是"该用别的白名单"——`EDUCATION_ALLOWLIST` 本身选得对（比泛用学术源更对口），只是当时只拿它测了错误语言的查询。

**处理**：把 `education` 正式加入 `VERTICAL_ROUTES`（`app/services/search_service.py`），初版把它和 `academic` 一起放进 `LANGUAGE_GATED_ROUTES`（中文查询跳过）——这次是有直接实测支撑的（英文 73% vs 中文 0%），不是套用 academic 结论的直觉扩展。但"跳过"本身是否是 education 域中文查询的最优处理，紧接着被 §9.5 推翻。

### 9.5 用户追问：项目最终面向中文母语者，"跳过中文"够不够

§9.2-9.4 的门控策略本质是"中文查询打不过英文语料库，那就少花这次请求"——对 `academic`（arxiv/IEEE 这类天然只有英文原始文献的语料库）成立，因为换个中文说法也搜不到对应的中文一手论文。但用户指出一个关键点：**项目最终服务的是中文用户，"跳过"不是真正的解决方案，只是止损**。复核后发现这个止损策略被过度套用了：`legal`/`policy`/`business`/`education` 的白名单本来就是清一色的西方/国际机构（eur-lex、wipo.int、oecd.org、eric.ed.gov……），中文查询打这些源命中率低，不是"中文语言本身劣势"，是**白名单的国别选错了**——问题从来不是"英文搜不到中文答案"，而是"没给中文查询配中文能找到答案的源"。

验证：把之前测过的中文查询原样保留，只把白名单换成中国官方一手源（`gov.cn`/`npc.gov.cn`/`moj.gov.cn`/`court.gov.cn`/`ndrc.gov.cn`/`mofcom.gov.cn`/`stats.gov.cn`/`moe.gov.cn` 等）：

| 域 | 换成中国官方源后的命中率 | 之前打西方白名单的命中率 |
|---|---|---|
| legal | **10/10（100%）** | 33%（§7.3，中文查询）|
| policy | **10/10（100%）** | 40%（§7.3，中文查询）|
| education | **5/5（100%）** | 0%（§7.5 初版，中文查询）|
| business | 5/10（50%，统计局类查询 5/5，"AI芯片出口管制"类因白名单里 csrc.gov.cn 不是对口权威源而 0/5） | 33%（§7.3，中文查询）|

四个域全面优于原白名单，legal/policy/education 甚至打平或超过英文查询打西方白名单的命中率（92%/73%）。这证明中文查询本身没有"先天劣势"——`academic` 那 9% 的低命中率是语料库本身只有英文原始文献的结构性限制，legal/policy/business/education 的低命中率是我们自己选错了白名单的国别，两者原因不同，之前用同一个"跳过"策略处理是把两种不同性质的问题混为一谈了。

**处理**：新增 `LEGAL_ALLOWLIST_ZH` / `POLICY_ALLOWLIST_ZH` / `BUSINESS_ALLOWLIST_ZH` / `EDUCATION_ALLOWLIST_ZH`，`education` 从 `LANGUAGE_GATED_ROUTES`（跳过）移出，改造 `search_vertical_dual()`：中文查询命中 `VERTICAL_ROUTES_ZH` 就换用对应中文白名单，而不是跳过或沿用西方白名单；当时 `academic` 还没有对应中文一手源，继续跳过（后被 §9.6 推翻——CNKI/万方付费墙问题依旧，但换了个思路测出别的中文源可用）。

12 题基准复测：新增 `-zh` 路由标记（如任务 06 GDPR 对比：`legal=26 / legal-zh=47`，任务 07 碳中和：`policy=44 / policy-zh=58`），总耗时 886.8s——与不做中文源替换的版本（922.4s）基本持平甚至略低，因为这是"换白名单"不是"多发请求"，成本不变，纯收益。数据存档：`benchmark/results/retriever_20260818_032024.json`。

### 9.6 用户追问：EN/ZH 都要"成规模"，逐路由审计域名数量

用户指出一个此前没系统检查过的问题：中英文白名单不能只看"有没有"，还要看"够不够"——单一域名撑起 100% 命中率不叫规模，是单点故障。逐路由清点域名数：

| 路由 | EN 域名数 | ZH 域名数 | 判断 |
|---|---|---|---|
| academic（science/technology） | 31 | **0** | 严重缺口——覆盖 8/12 基准任务的域完全没有中文源 |
| business | 15 | 5 | 偏薄，暂可接受 |
| legal | 13 | 7 | 相对均衡 |
| policy | 13 | 6 | 相对均衡 |
| education | 8 | **1** | 单点故障——§9.5 的 100% 命中率全部来自 `moe.gov.cn` 一个域名 |

两个真实缺口：`academic` 中文侧完全空白（此前 §9.5 判定"换不出源"直接跳过），`education` 中文侧规模过薄。

**education 扩容**：补测教育部考试中心（`neea.edu.cn`）、学信网（`chsi.com.cn`）后扩到 3 个域，命中率仍有 93%（14/15，新两个域本轮样本没测出命中，但作为教育部下属官方机构予以保留，换更多真实查询时再观察贡献）。

**academic 中文侧翻案**：§9.5 判"换不出源"是因为一直在找"中文版学术论文"（CNKI/万方，本来就稀缺且付费墙），换个思路——找中国官方科研机构本身发布的研究动态/成果通报，而不是论文本身：

| 候选域 | 命中贡献（PASS 次数） |
|---|---|
| `cas.cn`（中国科学院） | 10 |
| `ccf.org.cn`（中国计算机学会） | 4 |
| `cnki.net` / `nsfc.gov.cn` | 各 1 |
| `most.gov.cn` | 0（本轮未出现在结果里，仍保留） |

整体命中率 80%（16/20）。`cas.cn`/`ccf.org.cn` 是主力贡献者，其余域名贡献弱但仍保留——跟英文 `ACADEMIC_ALLOWLIST` 31 个域名本身也不是每个都同等强势是一样的设计取舍：广撒网，让 reranker/source_evaluator 自过滤。`academic` 因此从 `LANGUAGE_GATED_ROUTES` 移出，改用换源。

### 9.7 扩充到 10 个垂直域，对标 AnySearch 差距清单

在"规模是否达标"的审计之上，进一步追问：垂直源覆盖对比 AnySearch 是不是还是太少。§5 的差距 #1 之前列出 AnySearch 提到但本项目没有的域：finance/legal/health/code/ip/security——finance 已被 `business` 覆盖、legal 已有，真正的缺口是 **health/code/ip/security** 四个。用同一套实测方法论验证候选白名单：

| 域 | EN 命中率 | ZH 命中率 | 处理 |
|---|---|---|---|
| health | 100%（12/12） | 92%（11/12，nhc.gov.cn/nmpa.gov.cn/chinacdc.cn） | 接入 |
| code | 100%（12/12，几乎全部命中来自 github.com） | 未测（预期结构性英文语料，同 academic 早期误判前的情况） | 只接入 EN，中文查询走跳过 |

### 9.11 10 个垂直域补齐后，回头验证意图识别本身的准确率

过程中出现一次 LLM 瞬时 `InternalServerError`（`Expecting value: line 1 column 1`），被 `nodes.py::_llm_with_short_retry` 自动重试后成功，不影响最终统计。

**这个 97.1% 后来被证明偏乐观**——见 §9.12，35 条样本话题集中度太高、边界案例太少，掩盖了几个真实存在的系统性误判模式。

### 9.12 用户质疑样本量不够，扩到 92 条重测：准确率修正为 90.2%，发现三个系统性模式

用户明确指出 §9.11 的 35 条测试集"不够大和全面，测出来的准确率可能不是真的"。这是合理的质疑：§9.11 每个域只有 2 条清晰案例，边界案例每对只有 1 条，样本量小到不足以发现系统性偏差，只能发现孤立的偶然误判。扩大到 **92 条**，改进点：

- 每个垂直域清晰案例从 2 条扩到 **5 条**，且刻意跨子领域分散话题（如 `science` 覆盖物理/生物/天文/化学/地质，不再局限于容易和其他域混淆的 AI/科技相关话题），避免"域内话题单一"把偶然对齐算成普遍准确；
- 边界案例从 11 条扩到 **32 条**，每个对比至少 2-4 条不同话题，新增 `education` vs `science`（教学 vs 机制本身）、`business` vs `technology`（市场竞争 vs 技术架构）、`legal` vs `security`（法律责任 vs 技术防御）三组此前未覆盖的边界；
- `general` 清晰案例从 1 条扩到 5 条，全部选真正难定主导视角的问题（元宇宙、远程办公、老龄化、SDGs 等）；
- 英文查询从 3 条扩到 5 条，覆盖此前完全没测过英文的 `legal`/`policy`/`code`/`environment`/`education` 五个域。

**结果：83/92 命中，准确率 90.2%**（比 §9.11 的 97.1% 低 6.9pp）。按预期域拆分：

| 域 | 命中率 | 说明 |
|---|---|---|
| technology / science / policy / legal / business / education / health | 100%（或 legal 9/9、business 8/8 等小样本 100%） | 无问题 |
| security | 88%（7/8） | 1 处误判，见下 |
| environment | 80%（8/10） | 2 处误判，见下 |
| code | **62%（5/8）** | 3 处误判，系统性，见下 |
| general | **40%（2/5）** | 3 处误判，最严重，见下 |

三个可复现的系统性模式（区别于 §9.11 那种样本量为 1、无法判断是否系统性的孤立误判）：

1. **`code` vs `technology`，基础设施配置类问题几乎必错**：K8s 资源限制配置报错（OOMKilled）、PostgreSQL 连接池报错（too many connections）、SQL 索引优化，3/3 全部判成 `technology`，即便 intent 都正确判成 `how_to`。规律清晰：只要问题涉及数据库/容器编排/基础设施，LLM 倾向于把"报错怎么修"也当成"架构原理"处理，`code` 的判定实际上被压缩到了"应用层语言/框架代码"这个更窄的范围。
2. **`environment` vs `policy`，政策学措辞包裹环境议题时倒向 `policy`**：大气污染治理"国际经验"、《巴黎协定》"履约情况"，用政策学术语（国际经验、政策措施、履约）描述环境议题时 2/2 判成 `policy`；同一边界下用更偏生态/监测术语描述（PM2.5 监管标准、温室气体生态影响）时判对。规律是措辞而非议题本身决定归类。
3. **`general` 域近乎不可达**：5 条刻意设计成"无主导视角"的问题里，LLM 只认可 2 条，另外 3 条（元宇宙发展现状→`technology`、远程办公影响→`business`、SDGs 进展→`policy`）都被找到了一个"主导视角"强行归类。reasoning 显示 LLM 总能为任何宽泛问题构造出一个主导视角，`general` 的定义"仅在真正无主导视角时使用"门槛实际上很少被触发——这可能不是分类错误，而是 `general` 这个类目本身在当前 prompt 设计下过于保守，需要单独评估是否要放宽定义或接受"`general` 很少触发"是预期行为（因为 domain 只用于是否触发垂直路由，`general` 本来就不接任何垂直白名单，误判成某个具体域不一定是坏事——如果那个具体域的视角确实部分适用）。

**结论**：`code`/`environment`/`general` 三处的误判不是随机噪声，值得后续在 `planner.md` 里补充针对性的边界说明或反例；但本轮任务是"扩测试集验证准确率"，不包含改 prompt，改动留作后续任务。

验证脚本未入库（`verify_domain_intent.py`，一次性诊断脚本，遵循本项目对临时验证脚本不提交的惯例）。

### 9.13 根因：domain 曾是全局单标签，不是逐子问题——已修复

**根因**：§9.12 的三个系统性误判模式（`general` 近乎不可达、`code`/`technology` 边界模糊、`environment`/`policy` 边界模糊）共享同一个架构原因——`domain` 曾是**整个研究计划级别**的单一全局标签（`retriever_node` 用 `research_strategy.domain` 一个字段决定所有子问题是否走垂直路由），选一个具体域能让部分子问题吃到垂直源加成、选 `general` 则整个任务放弃，同时沾两个域的问题也没有"两个都要"这个选项，只能强行二选一。对照 AnySearch 的调用行为（`domain` 挂在每条查询而非整个任务、不确定时混合检索而非二选一、分类结果是路由提示而非排他标签，见 `docs/AnySearch技术原理与项目借鉴调研.md` §4.1-4.2）确认方向：把 domain 判断下沉到子问题级别。

**架构对比**：

```
改动前 —— domain 是整个研究计划级别的单一标签
════════════════════════════════════════════════════════════════
  Planner
    └─ research_strategy.domain = "business"   ← 只有这一个标签

  retriever_node（第 1 轮）
    全部子问题共用同一个 vertical_route(business)
    ┌────────────┬────────────┬────────────┐

    │  → business │  → business │  → business │  ← q1/q3 被迫套错域
    └────────────┴────────────┴────────────┘

  retriever_node（第 2+ 轮补证，_supplement_round 触发）
    follow_up_queries 被拍平成一条列表，sq_id 全部置空
    → 查不到任何子问题归属，整体退回 fallback_domain


改动后 —— domain 下沉到子问题级别，第 1/2+ 轮共用同一套路由代码
```

### 9.14 差距 #2 增量：边界子问题双域混合检索，不强制二选一

§9.13 只解决了 AnySearch 原则①（决策粒度是每条查询而非整个任务），原则②"不确定时是混合，不是二选一"还没有对应实现——`code`/`technology`、`environment`/`policy` 这类边界模糊的子问题，即使 domain 判断已经下沉到子问题级，仍然只能二选一，选中的那个域猜错了就完全拿不到另一个域的垂直源。

**架构对比**：

```
改动前 —— 每个子问题只有一个 domain，猜错了就完全错过对应垂直源
════════════════════════════════════════════════════════════════
  子问题："巴黎协定履约过程中的地缘政治障碍和公平性争议"
    domain = policy                     ← 只能二选一
                    │
                    ▼
        retriever_node → search_vertical_dual(query, "policy", POLICY_ALLOWLIST)
        → 只搜通用路 + policy 垂直路，即使这条子问题同样需要环境治理一手源，
          environment 垂直路完全没有机会命中


改动后 —— 真正跨两个域的子问题可以标 domain_secondary，两个域都搜
════════════════════════════════════════════════════════════════
  子问题："巴黎协定履约过程中的地缘政治障碍和公平性争议"
    domain = policy          domain_secondary = environment   ← 显式标两个域

                    │
                    ▼
        retriever_node → search_vertical_multi(query, ["policy", "environment"])
        ┌──────────────────────┬──────────────────────┐
        │ 通用路 + policy 垂直路 │ environment 垂直路     │  ← 并发拼接，URL 去重
        └──────────────────────┴──────────────────────┘
        （若两个 domain 解析到同一个 route_name，如 science+technology 都是
         academic，只搜一次，不重复请求）

  绝大多数子问题仍然只有一个清晰 domain，domain_secondary 留空 → 走原来的
  search_vertical_dual 单路径，不受影响、无额外成本
```

**改动清单**：

- `app/prompts/planner.md`：Sub-question Rules 新增 #6（`domain_secondary`，原 #6"Search queries"顺延为 #7）。明确这是"子问题真正同时需要两个域的一手源"才用的例外字段，不是"不确定就都填"的兜底选项；给了两个对应 §9.12 已验证的边界模式做校准：基础设施报错类问题（K8s/数据库报错）标 `domain_secondary: code`，政策学措辞包裹的环境议题标 `domain_secondary: environment`。Output Format schema 的 sub_questions[] 新增 `domain_secondary` 字段（可选，省略或 null）。
- `app/services/search_service.py::search_vertical_multi(query, domains, max_results)`：`search_vertical_dual` 的多域泛化版——通用路 + 每个 domain 各自解析出的垂直路并发检索，按 URL 去重合并；多个 domain 解析到同一 route_name（如 science/technology 都指向 academic）时只搜一次；domains 为空或全部解析不到 `VERTICAL_ROUTES` 条目时退化为纯通用搜索；中文查询换源/语言门控逻辑与 `search_vertical_dual` 一致。不改动 `search_vertical_dual` 本身（已验证过的单域路径零风险）。
- `app/graph/nodes.py::retriever_node`：新增 `sq_domain_secondary` 映射（过滤掉未设置、空值、和主 domain 相同的情况），`_search_tagged` 里子问题有合法 `domain_secondary` 时调用 `search_vertical_multi`，否则走原来的 `_vertical_route_for` + `search_vertical_dual`/`search` 单域路径不变。

### 9.15 差距 #3 + #4：跨源融合排序 + 结构化子域参数契约（绑定 academic 落地）

§5 表格里剩下两条一直标"backlog"的差距——跨源融合排序、结构化子域参数契约——这轮一起做。两者本质相关：#4 引入一个真正结构化的数据源后，它带来的字段（被引用数）恰好是 #3 融合排序最需要的权威性信号，不引入 #4 的话 #3 只能拿 Tavily 自己的相关度分数打分，信号来源单一。

**#4 选型：Semantic Scholar vs CrossRef，真实请求对比**

两个免费学术 API 里选一个绑定实现，不凭文档描述判断，直接打真实请求：

| 候选 | 实测结果 |
|---|---|
| Semantic Scholar | 匿名池**持续 429**（连续 4 次指数退避重试、单独拉长到 20s/30s 再试均失败），官方错误信息明确要求"apply for a key"——免费但需要额外申请注册，不满足"立即可用"前提 |
| CrossRef | 稳定可用，4 条测试查询 DOI 覆盖率 5/5；默认相关性排序比按被引用数排序明显更准（按被引排序会把无关但高被引的论文挤到最前面，如 "vLLM" 查询排出一篇 DNA 测序论文）；默认摘要覆盖率约 1/5，加 `filter=has-abstract:true` 后提到 5/5 |

**选定 CrossRef**：默认相关性排序 + `has-abstract:true` 过滤。

**架构对比**：

```
改动前 —— 通用路 + 垂直白名单路，按 URL 去重，通用优先拼接
════════════════════════════════════════════════════════════════
  查询 → 通用搜索(Tavily) ─┐
       → 垂直白名单搜索(Tavily) ─┤→ URL 去重 → 通用结果在前，垂直结果去重后追加
                                  （谁先被搜到就排在前面，不是排序，是拼接顺序）


改动后 —— 三路并发 + 可解释融合排序
════════════════════════════════════════════════════════════════
  查询 → 通用搜索(Tavily) ──────────────┐
       → 垂直白名单搜索(Tavily) ─────────┤
       → 结构化数据源(CrossRef，仅       ├→ _fuse_and_rank()
         academic 路由 + 非中文查询时)  ┘     │
                                              ├─ URL 去重（同 URL 保留权威信号更强的版本）
                                              ├─ authority：CrossRef 用 log1p(被引数)
                                              │  归一化；垂直白名单固定 0.75；通用路
                                              │  用 tavily_score，无分数给中性 0.5
                                              ├─ diversity：同来源（域名，CrossRef 按
                                              │  DOI 出版社前缀分组）出现次数越多分数
                                              │  衰减越多，全局静态计数，非逐条 MMR
                                              └─ freshness：有发表年份的按距今年数线性
                                                 衰减，无年份给中性分
                                              → 加权求和（0.5/0.3/0.2）排序
```

**改动清单**：

- `app/services/academic_api.py`（新文件）：`search_crossref(query, max_results)`，对接 CrossRef `/works` 接口，返回带 `doi`/`citation_count`/`venue`/`published_year` 的 `SearchResult`，摘要清洗掉 JATS XML 标签后同时填进 `snippet`/`raw_content`（有摘要就不用再爬一次）。
- `app/models/source.py::SearchResult`：新增 `doi`/`citation_count`/`venue`/`published_year` 四个可选结构化字段（差距 #4），`provider` 新增 `"crossref"` 取值，`search_route` 新增 `"academic-structured"` 取值。
- `app/services/search_service.py`：
  - `STRUCTURED_ROUTE_PROVIDERS: dict[str, ...]`：route_name → 结构化数据源查询函数，目前只有 `"academic": search_crossref` 一条，不为其余 9 个路由强行凑数。
  - `_fuse_and_rank()`（差距 #3）：URL 去重 + 三维度可解释融合评分排序，替代原来的拼接逻辑。
  - `search_vertical_dual()`/`search_vertical_multi()`：命中 `STRUCTURED_ROUTE_PROVIDERS` 且查询非中文时，额外并发一路结构化源检索；最终统一走 `_fuse_and_rank()`。

**过程中发现并修复的一个真实 bug**：第一版 `_fuse_and_rank` 用 URL 域名（netloc）做 diversity 分组，真实数据测出问题——CrossRef 结果的 URL 统一是 `doi.org/<DOI>`，5 篇分属不同期刊/出版社的论文全部收敛成同一个 netloc `doi.org`，被 diversity 逻辑误判成"同一来源重复出现"，全部结果集体被压低排名（574 次被引的论文原本该排前列，实测排到了第 7 名）。修复：CrossRef 结果改用 DOI 的 registrant 前缀（如 `10.3389` 对应 Frontiers）做分组键，同一出版社反复出现时仍会被惩罚（期望行为），不同出版社则各自算独立来源。修复后同一条查询里该论文排到第 5 名。

**关键数据**：

### 9.16 补第二个结构化数据源：arXiv（补 CrossRef 的覆盖盲区）

§9.15 的"已知局限 #1"记了一笔：CrossRef 全文检索对小众/前沿技术话题匹配偏松。根因其实更具体——**CrossRef 索引的是已经正式发表、带 DOI 的文献**，vLLM PagedAttention 这类系统研究论文往往先挂 arXiv 预印本，几个月甚至一两年后才正式发表（有的永远只挂会议 workshop，不走期刊/会议 DOI 流程），CrossRef 天然覆盖不到这段时间差。arXiv 官方 API 直接补这块，而不是替代 CrossRef——两者互补：CrossRef 有被引数、期刊、正式发表年份，arXiv 有及时性和更宽的前沿研究覆盖。选型沿用 #4 的路数：免费、不用注册，未做额外对比（跟 CrossRef 不是竞争关系，不存在"二选一"的比较问题）。

**接入过程中真实测出两个问题**：

1. **arXiv API 官方给的是 `http://export.arxiv.org`，实测已强制 301 跳转到 `https`**，httpx 默认不跟随重定向，第一版直接请求失败返回 0 条（不是"没有结果"，是请求都没打成功）。改用 `https` 地址 + `follow_redirects=True` 修复。
2. **查询词用 `AND` 强制连接在长查询上会过严**：最初设想跟 CrossRef 一样"信任 API 自己的相关度排序"，但 arXiv 的查询语法需要显式给布尔连接符，裸拼接多词会被当成隐式 OR，召回面过宽（同一个四词查询命中数从 0 冲到 20 万+）。改成显式 `AND` 后短查询（2 词）效果很好——"vLLM PagedAttention" 能把目标论文排到第一；但 Planner 生成的查询常有 4 个以上关键词，要求全部同时出现在标题/摘要里，真实测试里直接 0 命中（"vLLM PagedAttention inference acceleration" 四词 AND，因为目标论文只包含其中 2 个词）。最终定为**两级策略**：先按 AND 精确匹配，0 条命中时再退化成裸词拼接的宽松匹配（隐式 OR）兜底，两级都失败才真的判定"arXiv 没有相关结果"。

**架构改动**：`STRUCTURED_ROUTE_PROVIDERS` 从 `dict[str, 单个查询函数]` 改成 `dict[str, 查询函数列表]`——academic 路由现在对应 `[search_crossref, search_arxiv]` 两个数据源，命中时并发查两个而不是一个，`search_vertical_dual`/`search_vertical_multi` 的并发调度、异常隔离、日志都相应改成按列表遍历，其余路由（业务/法律/政策等）不受影响，仍是空列表。

**关键数据**：

| 验证项 | 结果 |
|---|---|
| `search_arxiv` 真实请求（"vLLM PagedAttention"，2 词） | AND 精确匹配直接命中，目标论文排第 1 |
| `search_arxiv` 真实请求（"vLLM PagedAttention inference acceleration"，4 词） | AND 精确匹配 0 条 → 自动降级宽松匹配 → 目标论文进入返回的前 5 条（但不再是断层领先） |
| `search_arxiv` 真实请求（CRISPR off-target 查询） | AND 精确匹配直接命中 3 条相关论文，未触发降级 |
| 结构化路接线单测（mock，4 场景，含 arXiv 更新后重跑） | 全部通过：英文 academic 查询同时触发 CrossRef + arXiv、中文查询两个都不触发、无结构化源路由不触发、多域检索里 academic 命中各触发一次 |
| `search_vertical_dual` 真实端到端（vLLM PagedAttention 四词查询） | 20 条候选（10 tavily + 5 arxiv + 5 crossref）融合排序；目标论文经 3 条不同路径入选候选池（Tavily 通用路第 2 名、Tavily 学术白名单路、arXiv 结构化路第 10 名） |
| 既有回归（融合评分单测 12 项、多域路由 mock 4 场景） | 全部复测通过，未受影响 |

**已知局限（如实记录，未解决）**：

1. ~~同一篇论文经不同 provider 命中时不会被去重~~——**已在 §9.17 修复**。
2. **arXiv 结果的 authority 打分没有区分"标志性论文"和"普通预印本"**：arXiv 不追踪引用数，`_authority_score` 退到与其它垂直白名单命中同档的 0.75 固定分——四词查询的真实排序结果里，一篇小工具论文（"vLLM Hook v0"）排在了 PagedAttention 原论文前面，纯粹因为 freshness 维度占了便宜（更新发表）。没有真实标注数据支撑"该给预印本打多少折扣"，如实按经验默认值处理，不假装能精确量化。
3. **AND/OR 两级降级策略本身未做过大样本命中率统计**，只用 3 条真实查询验证了机制按预期切换，还没有测过"降级后的宽松匹配对多数 Planner 生成的长查询是否真的够用"这类规模化问题。

### 9.17 跨 provider 去重：规范标识符（DOI/arXiv ID）优先于 URL

§9.16 局限 #1 记的问题——同一篇论文经不同 provider 命中时因 URL 形式不同不会被去重——这轮修。

**先查 AnySearch 怎么做的：查不到**。`docs/AnySearch技术原理与项目借鉴调研.md` 明确把"去重规则"列进了未公开清单（该文档 §2，与意图分类器、融合公式并列），没法照抄。转向业界公认做法：OpenAlex、Semantic Scholar、Zotero/Mendeley 这类系统合并"同一篇论文的不同来源记录"时，标准做法是按 DOI/arXiv ID 这类跨来源稳定的规范标识符做实体消歧（entity resolution），不是字符串去重——URL 会因为镜像站、协议头、版本号、爬虫路径不同而变化，但一篇论文的 DOI/arXiv ID 是不变的。

**实现**：`_fuse_and_rank` 的去重键从原始 `r.url` 换成 `_canonical_key(r)`：优先用结构化字段里已有的 `doi`（CrossRef 直接给的），没有则用正则从 URL 里抽 DOI（`10\.\d{4,9}/...`）或 arXiv ID（`arxiv\.org/(?:abs|pdf|html)/...`，剥掉版本号后缀），两者都没有才退回原始 URL，与改动前行为一致。同时把去重的"保留哪一份"从原来简单的"是否命中垂直白名单"两档，扩成三档优先级：结构化数据源（有 DOI/被引数/年份等真字段）> 命中垂直白名单的通用搜索 > 纯通用搜索——不再是"先到先得"，而是保留信息量最大的那份。

**真实数据测出并修复了一个 bug**：第一版 arXiv ID 正则只认 `arxiv.org/abs/` 和 `arxiv.org/pdf/` 两种路径，真实跑 vLLM PagedAttention 查询时发现 Tavily 实际爬到的是 `ar5iv.labs.arxiv.org/html/2309.06180`——`ar5iv` 是 arXiv Labs 官方维护的 HTML 渲染镜像（域名里仍含 `arxiv.org` 子串），但路径是 `/html/` 不是 `/abs/`，第一版正则漏判，改动后仍是 2 条而不是 1 条。加上 `html` 这个路径分支后，同一条查询里 PagedAttention 论文从 3 条实例（Tavily 通用路 + Tavily 学术白名单路 + arXiv 结构化路）正确合并成 1 条，保留信息量最大的 arXiv 结构化版本。

**关键数据**：

| 验证项 | 结果 |
|---|---|
| `_canonical_key`/`_extract_doi`/`_extract_arxiv_id` 单测 | 6 个场景全过：同一篇 arXiv 论文 3 种 URL 形式合并为 1、DOI 嵌在出版商 URL 里能与 CrossRef 合并、DOI 不嵌在 URL 里时如实保留为 2 条（见下方局限）、不同论文不误合并、无标识符的普通网页仍按 URL 去重（不回归）、抽取函数字段/URL 双来源正确性 |
| `search_vertical_dual` 真实端到端（vLLM PagedAttention 四词查询，重跑 §9.16 同一条查询） | 该论文出现次数从改动前的 **3 次降到 1 次**；总候选数相应从 20 条降到 19 条（去重多合并了 1 条），其余排序逻辑不受影响 |
| 既有回归（融合评分单测 12 项、结构化路接线 4 场景、多域路由 mock 4 场景） | 全部复测通过，未受影响 |

**已知局限（如实记录，如实划定这次修复的边界）**：

1. **只有 URL 里实际嵌了 DOI/arXiv ID 的情况才能被合并**：Springer/BMC/PLOS 这类出版商的文章 URL 本身就包含完整 DOI 路径，能合并；但 Nature/Science 这类用自己的短 ID scheme（不含 `10.xxxx/` 前缀）的出版商页面，正则抽不出 DOI，仍会被当成两条不同结果——已用真实 URL 形态测过这个边界（场景 2b），不是漏测的假设。
2. **没有做标题/作者模糊匹配兜底**：这是上一轮明确讨论过、按你的决定暂不做的部分（误判率上升、缺少数据支撑该收多紧），先看这版规范标识符方案的实际效果再决定要不要加。

**范围说明**：同 §9.16，只做"规范标识符优先"这一版，不含标题模糊匹配兜底。

验证脚本未入库（`verify_canonical_dedup_unit.py`，一次性诊断脚本）。

### 9.18 全量 12 题基准验证：真实并发下测出 CrossRef/arXiv 限速代价

前几轮验证（§9.15-§9.17）都是单条查询或小规模 mock 场景，没有在这个项目真正的基准负载下测过。这轮用 `benchmark/retriever_benchmark.py`（12 题全集，并发 2，与本文档历史"总耗时"数据同一套方法论）跑一次完整回归，同时作为 §9.15-§9.17 三项改动（CrossRef 接入、arXiv 接入、跨 provider 去重）合在一起的真实负载验证。

**结果：12/12 任务全部成功，子问题归属全覆盖，无崩溃**——降级安全按预期工作。总结果 2495 条，命中垂直路由（含结构化路）1529 条，其中 academic-structured（CrossRef+arXiv 结构化路合并去重后）472 条。

**但真实测出一个新问题，之前的小规模测试没暴露**：12 个任务并发跑起来后，CrossRef 和 arXiv 都出现了持续的 429——CrossRef 43 次请求失败中 41 次是 429，arXiv 68 次请求失败**全部**是 429。两者都是免费匿名访问、没有为本项目单独分配过配额，在"12 个任务 × 每任务 15~28 个查询 × 命中 academic 域时每条查询并发打 2 个结构化源"这个量级下，会撞上它们各自的全局限速（不是账号级限速，是全局匿名池限速，这点上 CrossRef 和之前被否决的 Semantic Scholar 处境类似，只是限速阈值更宽松，宽松到单条/少量查询测不出来）。代码本身按设计优雅降级——单条结构化请求 429 只是让那条查询拿不到结构化结果，不影响其余请求，也不会把整个任务拖垮，所以最终 12 个任务仍然全部"全覆盖"——但意味着**结构化数据源在生产环境的实际到达率，比单条查询测试时乐观得多**。

**总耗时也如实变化了**：1291.8s（并发 2），高于本文档记录的上一个 12 题基准数字 886.8s（§0，§9.9 之后、接 CrossRef/arXiv 之前的版本，同为并发 2）。最可能的原因不是代码变慢，是请求量本身变大了——以前 academic 域的一条查询只发 2 个请求（通用路 + 学术白名单路），现在多发 2 个（CrossRef + arXiv），即使这 2 个最后 429 失败，网络往返的等待时间仍然要花，43+68=111 次失败请求的等待时间累加起来是实打实的耗时，不是路由逻辑本身变慢。

**已知局限（如实记录，未解决）**：

1. **CrossRef/arXiv 的免费匿名访问在这个项目的真实并发量级下会被限速**，目前没有做任何客户端限速/重试/退避处理（结构化源请求失败就直接放弃这条查询的结构化结果，不重试）——本轮结果显示"不重试"本身没有引发级联问题（没有拖垮任务），但意味着结构化数据源的实际覆盖率是概率性的，同一批查询不同时间跑，academic-structured 命中数会因为限速窗口不同而有明显波动，不是稳定可复现的数字。
2. **12 题基准总耗时从 886.8s 涨到 1291.8s（+45.7%）**，代价来自新增的网络请求量本身，是"接了 2 个新数据源"的直接成本，暂未评估是否需要给结构化源单独加一层限速/并发控制来换回耗时（如降低这两个 provider 的调用频率，或给 academic 域整体加一个独立的、更保守的并发上限），本轮不做，如实记录待决策。

**范围说明**：这是一次验证性基准运行，不属于 §9.15/§9.16/§9.17 里明确定义的实现范围，本节只记录用真实负载测出的数据和新发现的问题，不包含任何限速/重试相关的代码改动。

结果已保存（未入库）：`benchmark/results/retriever_20260820_122506.json`。

### 9.19 给 CrossRef/arXiv 各设进程级并发上限

承接 §9.18 局限 #2 的决策——先做能立即落地、代价最小的一步：给两个结构化源各加一个进程级 `asyncio.Semaphore`，同一时刻在飞的请求数超过上限就排队等待，模式与 `llm_service.py` 的 `_llm_semaphore` 完全一致（只在真正发起 HTTP 请求时占槽位，不含 httpx 客户端建连等其它开销）。

**上限怎么定的**：不是拍脑袋。arXiv 官方 API 使用须知明确写了"不超过每 3 秒 1 个请求"，是三个源里最严格的书面约束，因此给它更保守的上限（`arxiv_max_concurrency=2`）；CrossRef 没有同等明确的书面速率条款，只在"polite pool"文档里建议带 `mailto`（已在用），给稍宽松一档（`crossref_max_concurrency=3`）。两个数字都进了 `app/core/config.py::Settings`，可通过环境变量覆盖，不是硬编码。

**这一步解决什么、不解决什么**：信号量压的是"同一时刻并发在飞的请求数"，把突发请求错峰摊开，直接针对 §9.18 测出的"12 个任务同时开工时瞬间打出去一大批请求"这个触发场景；但**不减少总请求量**，也**不是**真正的令牌桶限速（不保证"3 秒 1 个"这种时间间隔约束，只保证"同一时刻最多 N 个在飞"）——如果 arXiv 的限速是按滑动时间窗口算而不是按并发数算，窄并发但高频率地打（比如 2 个槽位但请求处理极快、间隔仍 <3 秒）理论上还是可能撞限速。§9.18 记的"不重试/不退避"和"命中数不稳定可复现"两个局限本轮都没解决，如实结转。

**验证方式**：mock `httpx.AsyncClient.get` 为一个耗时的假请求，10 个并发调用同时发起，用锁记录"同一时刻正在真正发请求"的峰值数量（脚本见 `verify_provider_semaphore.py`）——CrossRef 实测峰值精确等于配置的 3，arXiv 精确等于配置的 2，确认信号量按预期生效。未跑真实网络负载重新验证 429 是否減少（那需要重跑一次 §9.18 同等规模的基准，成本较高，本轮先以确定性 mock 验证机制本身正确为准）。

**范围说明**：只做并发上限这一步，不含重试/退避、不含把两个源从"进程级并发闸门"升级为"跨进程令牌桶限速"（`llm_service.py` 另有 Redis 令牌桶方案应对跨 worker 进程限速，这两个源目前请求量级远低于 LLM 调用，暂未同等处理）。

### 9.20 重跑 12 题基准：并发上限对两个源效果分化，不是都有效

§9.19 只用 mock 验证了信号量机制本身生效，没有验证它是否真的降低了 §9.18 测出的 429 率。这轮补上：同样用 `benchmark/retriever_benchmark.py`（12 题全集，并发 2）重跑一次，直接和 §9.18 的数字对比。

**结果是分化的，不是"改动生效"这么简单的结论**：

| 指标 | §9.18（无并发上限） | §9.20（加了并发上限） | 变化 |
|---|---|---|---|
| CrossRef 请求失败 | 43 次（41 次 429） | 2 次（2 次 429） | 大幅下降 |
| arXiv 请求失败 | 68 次（68 次 429） | 74 次（74 次 429） | 未改善，反而略高 |
| 总耗时 | 1291.8s | 1303.4s | 基本持平（+0.9%） |

**CrossRef 这边改动生效**：43 次失败压到 2 次，`crossref_max_concurrency=3` 把突发并发摊开后，确实躲开了大部分限速窗口。

**arXiv 这边改动没生效**：74 次失败、全部是 429，比改动前的 68 次还多（考虑到两次运行 Planner 各自重新生成子问题/查询，实际发出的 academic 域查询数量本身不严格相等，68→74 不能直接读成"变差了"，但至少可以确认——**没有观察到任何改善**，429 率仍接近饱和）。这印证了 §9.19 写在"不解决什么"里的推测：`arxiv_max_concurrency=2` 限的是"同一时刻并发数"，不是请求间的时间间隔；只要两个槽位轮流快速放行，短时间内还是能打出远超"每 3 秒 1 个"的请求频率，触发的是 arXiv 按时间窗口算的限速，并发闸门这个机制天然管不住。

**总耗时没有改善**：1291.8s → 1303.4s，几乎和 §9.18 持平，没拿回之前 +45.7% 的耗时代价。这与"CrossRef 大幅改善、arXiv 没改善"的结果是一致的——arXiv 请求量占比更高、429 更密集，是耗时的主要贡献者，只优化 CrossRef 一侧对总耗时影响有限。

**结论**：这次改动对 CrossRef 有效、对 arXiv 无效，**不能笼统汇报为"并发限流解决了限速问题"**。如果要真正解决 arXiv 侧的限速，下一步大概率要换成按时间间隔控制的限速器（如令牌桶/固定间隔发请求，保证请求间隔 ≥3 秒），而不是继续调小并发数——本轮不做，留待决策。

**范围说明**：这轮只做验证性重跑，未做任何进一步代码改动；academic-structured 总命中数和总结果数（635 条 / 2740 条）比 §9.18 的（472 条 / 2495 条）更高，但两次运行 Planner 生成的子问题/查询并不相同（LLM 非确定性），这两个数字不构成同批次对照，不据此下"命中变多了"的结论，只作为附带记录。

### 9.21 诊断 arXiv 并发上限为何无效：真实成因是短窗口累计请求配额，不是并发数

§9.20 只确认了"arXiv 侧改动没生效"这个结果，没确认原因。这轮直接绕开 `search_arxiv()`/`retriever_node`，用最原始的 `httpx` 请求分四轮直接打 arXiv 官方 API，逐步排除假说，脚本见 `diagnose_arxiv_429*.py`：

1. **单发一个请求 + 间隔递增连续发送**（0s/1s/3s/5s/10s gap）：全部 200。排除"进程/IP 被永久封禁"。
2. **真并发 2/3/5 个**（`asyncio.gather`）：全部 200。排除"瞬时并发数触发限速"这个此前一直以来的假设——`arxiv_max_concurrency` 想解决的问题从一开始就不是真正的触发条件。
3. **严格串行零间隔连发 10 个 / 用生产同款"并发上限=2"节流打 40 个（6 秒内打完）**：全部 200。排除"零间隔连发少量请求"。
4. **用生产同款"并发上限=2"节流持续打 120 个请求**：**前 20 个（约 7 秒内送出）全部成功，第 21 个开始转为持续 429**，后面 99 个全部失败。

**根因确认**：arXiv 的限速是**短时间窗口内的累计请求数配额**（实测量级约"20 个请求 / 7 秒"），不是"同一时刻并发数"。`asyncio.Semaphore` 限制的是"同一时刻最多几个在飞"，对"单位时间内总共发了多少个"完全不设防——并发=2 时每个请求约 0.3~0.6s 完成，一有空位立刻补下一个，实际吞吐仍能跑到每秒 3~6 个，几秒内就能把配额打穿，跟不设并发上限时几乎没有区别。这就是 §9.20 测出"arXiv 侧无改善"的直接原因：`arxiv_max_concurrency=2` 从设计动机上就没对准真正的触发条件。

**恢复时间**：撞到限速后连续探测，累计等待约 298 秒（176s + 122s，跨两轮探测脚本）后恢复 200，量级在 5 分钟左右。不排除今天在短时间内反复跑基准+诊断脚本，冷却期被多次触发/顺延，这个数字不是一次干净独立的测量，但至少确认了冷却期是"分钟级"而非"秒级"——用固定间隔限速器兜底时，间隔本身（如 3 秒）远比冷却期的存在更关键：只要不撞线，就不会付这几分钟的代价。

**这对 §9.19 的判断意味着什么**：`arxiv_max_concurrency` 这个配置项本身不是错误设计（并发闸门对 CrossRef 确实有效，见 §9.20），但对 arXiv 选错了要解决的问题——arXiv 需要的是**请求速率限制器**（固定请求间隔或令牌桶，例如强制两次请求间隔 ≥0.35s 甚至更保守地对齐官方建议的 3s），而不是并发数上限。两者是两个不同维度的节流，分开验证之前误以为"两者应该有同等效果"是不成立的。

**范围说明**：本节只做诊断，不改代码。是否要把 `arxiv_max_concurrency` 换成/补充一个真正的速率限制器（如固定间隔发请求），本轮不做，留待决策。

### 9.22 给 CrossRef/arXiv 接上跨进程速率限制器（Redis 令牌桶），两个源都做

用户决定两个源一起做，且要求"彻底避免问题"。§9.21 已经诊断清楚两个源的限速机制本质不同：arXiv 是短时间窗口累计请求数型（约 20 个/7 秒），CrossRef 是瞬时并发连接数型——动手前先补测了一下 CrossRef 的真实阈值（此前只测过生产负载下的结果，没专门测过边界）：瞬时并发 3/5/8 个全部成功，12 个开始零星失败（9/12），20 个近半失败（9/20）。现有 `crossref_max_concurrency=3` 本地信号量已经在这个安全范围内，问题是**本地信号量只在单进程内生效**——这个项目是多 worker 部署（`WorkerCount` 可配置多开），N 个 worker 各自独立持有一份信号量，真实聚合并发是 N 倍，纯本地闸门防不住跨进程叠加超限，对 CrossRef 和 arXiv 都一样。

**实现**：复用项目里已有的 `RedisRateLimiter`（`app/services/rate_limiter.py`，令牌桶，Lua 脚本原子读-补充-扣减），跟 `llm_service.py` 给 LLM 调用做跨进程限速是同一套机制、同一种接线方式——在本地 `asyncio.Semaphore` 之前先 `await get_rate_limiter().acquire(bucket, rate, burst)`，等待期间不占本地并发槽位；Redis 不可用时 `acquire()` 直接放行，由本地信号量继续兜底（降级安全，不引入新的单点故障）。落地在 `app/services/academic_api.py` 的 `search_crossref()` 和 `_query_arxiv()`。

**参数**（`app/core/config.py::Settings`）：

| 配置项 | 值 | 依据 |
|---|---|---|
| `arxiv_rate_limit_per_sec` | 0.33 | 对齐 arXiv 官方使用须知"不超过每 3 秒 1 个请求"，不贴着实测的"20 个/7 秒≈2.86/s"这条边界走——踩线的代价是约 5 分钟冷却期（§9.21），值得留足安全边际 |
| `arxiv_rate_burst` | 1 | 不给突发余量，严格串行节流 |
| `arxiv_rate_limit_max_wait` | 120（默认 30 不够用） | `RedisRateLimiter.acquire()` 默认超时 30s 会放弃排队直接放行——一个 deep 任务同时冒出十几个 academic 查询很正常，按 0.33/s 排到队尾轻松超 30s，默认值会让排在后面的请求提前放行、变相制造突发，正好撞回"短窗口累计请求数超限"这个根因，因此拉长到 120s，宁可任务慢一点也不再制造新的突发 |
| `crossref_rate_limit_per_sec` / `crossref_rate_burst` | 3.0 / 3 | 实测瞬时并发 ≤8 稳定成功，这里对齐已验证有效的本地并发上限（§9.20 测出把失败从 43 次压到 2 次），令牌桶主要是给多 worker 场景兜底，留数倍安全边际，不是本地闸门不够格 |

**验证（真实网络 + 真实 Redis，非 mock）**：复刻此前打崩两个源的并发场景——15 个 arXiv 查询同时发起（此前约 20 个/7 秒就会撞线）、20 个 CrossRef 查询同时发起（此前测出 12 个起零星失败）。结果：**两边全部成功，0 个失败，日志里没有一条 429**。arXiv 侧因为 0.33/s 节流，15 个查询（含 AND 精确匹配 0 条触发的宽松匹配二次请求，实际发出约 20+ 个请求）耗时 65.0s，是预期的代价——用等待时间换稳定性；CrossRef 侧因为 rate=3/s 已经比瞬时并发安全阈值宽松很多，20 个查询仅耗时 7.0s，几乎没有额外代价。

**这一步解决了 §9.18/§9.20/§9.21 一路留下的问题吗**：解决了根因层面的问题——两个源现在都有跟各自真实限速机制匹配的节流手段，不再是"选错维度"，且验证用的并发规模就是实测会撞线的规模。**没有解决**、也不在这轮范围内的：多 worker 场景下的联合验证（本轮验证是单进程内发起的并发，Redis 令牌桶的跨进程效果本身是 `rate_limiter.py` 既有设计、LLM 调用那条线已经在生产跑，但没有专门为 CrossRef/arXiv 补一次多进程联合测试）；也没有重新完整跑一次 12 题基准做端到端总耗时对比（arXiv 侧限流后单个 deep 任务的 academic 域检索会明显变慢，对总耗时的影响需要专门测，如实标注未测）。

本节是真实网络验证，不是标准基准框架跑出来的，没有生成 `benchmark/results/` 下的结果文件；验证脚本 `verify_rate_limiter_real.py`（scratchpad，未入库）。

### 9.24 用干净起点压力测试复核：§9.23 的"历史包袱"推测不成立，需要修正结论

§9.23 结尾建议"找个没有历史干扰的时间窗口再跑一次交叉验证"，这轮就是做这件事——先单发探测确认当前 arXiv 处于干净状态（200），再立刻跑一次同规模 12 题基准。

**结果推翻了 §9.23 的乐观推测**：arXiv 这次失败 67 次，比 §9.23 的 32 次还多，而且**不是集中在开局**——分布在日志第 153~852 行（总日志 1315 行），跨度覆盖了运行的大部分时间段，抽样看失败最密集的一段（约 90 行连续日志），里面**没有一次成功**，来自好几个不同任务、不同子问题的查询混在一起连续失败。这说明 §9.23"大概率是运行开始时的历史冷却尾巴"这个推测站不住——如果只是尾巴，干净起点跑出来的应该接近 0 次，不会比上一轮还多。

**排除了限流器本身失灵的可能**：逐项核对——`arxiv_rate_limit_enabled/per_sec/burst/max_wait` 配置值与预期一致（0.33/1/120，未被 `.env` 覆盖）；全程 0 次"限流累计等待超"放弃排队日志，说明**每一次 arXiv 请求都是在拿到令牌桶正式发放的令牌后才发出的，请求间隔严格遵守了 ≥3 秒**。也就是说，机制层面限流器完全按设计工作，问题不在这里。

**修正后的结论**：即使请求间隔严格遵守"≥3 秒"这个比官方建议还保守的节奏，arXiv 依然会连续拒绝一长串请求，且不是我们能靠调整发送节奏解决的。更接近事实的解释是——arXiv 一旦因为某个触发条件进入拒绝状态（具体触发条件仍不明确，可能不是纯粹"我们自己的请求节奏"这一个变量，也可能跟 arXiv 服务端当时的全局负载或更长周期的累计配额有关），**接下来一段时间（跟 §9.21 测出的约 5 分钟冷却期同量级）会无差别拒绝，不管后续请求发得多克制**。当天测试量本身可能也是促成因素之一（今天在诊断和多轮基准里累计已经发出上千次 arXiv 请求），但"清空短期冷却尾巴"不足以保证下一次就干净——这轮压力测试就是反例。

**这不影响任务本身的正确性**：12 个任务依然全部"全覆盖"，CrossRef 侧继续 0 失败并顶上更多命中，academic-structured 总命中 580 条（仍然健康）。降级机制按设计工作——单条 arXiv 查询失败不影响子问题拿到答案，只是拿到的结构化信号少了一些。

**对"彻底避免问题"这个目标的诚实结论**：客户端限流器能做到的是"不主动制造额外的突发/不亲手把请求发得比 arXiv 能承受的更密"——这一点已经验证生效（CrossRef 完全解决，且从没触发过放弃排队的降级分支）。但 arXiv 匿名访问在这种持续多任务并发的压力下，**不能保证零 429**，无法靠调小发送节奏这一个维度彻底根治，可能已经触达比"客户端请求节奏"更高层的限制（服务端全局负载 / 更长周期配额 / 匿名池固有不稳定性），这些不是纯客户端手段能覆盖的。已实现的方案仍然值得保留（把可控的那部分问题解决了，且不劣化 CrossRef），但"彻底避免"这个说法本身需要修正为"降低发生概率、不主动恶化，并继续依赖既有的优雅降级兜底"。

**范围说明**：本节只做复核测试，不改代码；是否要进一步投入（如申请 arXiv API key 获得更高配额、探索是否存在更长周期的配额限制并相应降低整体调用频率），本轮不做，留待决策——鉴于收益边际递减（任务正确性本身没受影响），不一定值得继续投入。

### 9.25 分速率压力测试找平衡点：现有配置本身没错，问题在"一旦触发冷却，纯拼节奏救不回来"

§9.24 说"不能保证零 429"，但没有专门测过"到底多慢才安全"这个更直接的问题——现有 `arxiv_rate_limit_per_sec=0.33` 是对齐官方建议拍的，没有实测校准过。这轮用两组独立实验找真实平衡点，脚本见 `find_arxiv_balance_point*.py`。

**实验一：单流严格串行，分别测 0.15/s、0.33/s（现值）、0.6/s，每档连发 24 个，档间隔 6 分钟冷却**：

| 速率 | 结果 |
|---|---|
| 0.15/s | 24/24 全部成功 |
| 0.33/s（现值） | 24/24 全部成功 |
| 0.6/s | 从第 20 个开始失败，最终 20/24 成功（失败率 17%） |

**确认了一个真实存在的平衡点**，且现有 0.33/s 的设置在安全一侧——0.6/s 的失败起点（约 20 个请求 / 33 秒）跟 §9.21 测出的"约 20 个/7 秒"量级一致，是同一个短窗口配额在起作用，只是换了个更慢的速率把触发时间往后推了。

**实验二：分两部分排查§9.24 那 67 次失败的真正原因是不是"生产代码允许并发=2"**：

- **A. 单流串行 0.33/s 拉长到 80 个**：开始前探测就已经是 429——说明这次是在还没恢复的状态下起跑的，全部 80 个请求无一例外全部失败，**持续 240 秒、每次都规规矩矩等了 3 秒以上才发，没有一个能穿透冷却期**。这不是本次实验设计的失败，反而是最有力的证据：**一旦真的进入冷却状态，拼节奏没用，唯一变量是时间**。
- **B. 冷却 6 分钟后重新探测确认干净，用生产同款"并发上限=2、整体授权节奏仍是 0.33/s"发 40 个**：**40/40 全部成功，0 次失败**。

**这推翻了"并发=2 是罪魁祸首"的猜测**：在确认干净的起点上，并发=2 叠加 0.33/s 节奏完全没有问题，跟严格单流一样干净。也就是说 §9.24 那 67 次失败，大概率不是"允许 2 个同时在飞"这个设置的问题，现有生产配置（`arxiv_max_concurrency=2` + `arxiv_rate_limit_per_sec=0.33`）本身是经过验证的合理组合。

**一个更值得注意的细节**：本节开头做完实验一的最后一档（0.6/s，触发了 4 次失败）后，手动探测过一次是 200（干净），但写完实验二的脚本、间隔了几分钟再跑，脚本自己第一次探测又变回了 429。这段时间里没有对 arXiv 发过任何请求，状态却从干净变回了受限——**说明是否处于冷却状态这件事，不完全由我们自己的请求行为决定**，可能跟 arXiv 服务端当天的全局负载、或者一个记忆窗口比单次"约 5 分钟冷却期"更长的信誉/配额机制有关（今天測试量本身也已经很大），这部分不是纯客户端调参能控制的。

**修正后的完整认识**：

1. 现有配置（0.33/s、burst=1、并发=2）经两组独立实验验证是安全、合理的组合，不需要再往更保守调（0.15/s 也没有额外收益，0.33/s 已经在安全区间内）。
2. 真正的风险点不是"稳态节奏没控制好"，而是"是否会被判定进入冷却状态"这件事本身有我们控制不了的成分，一旦触发，冷却期是硬下限，重试/放缓请求都换不回时间。
3. 由此产生一个还没做的改进思路（本轮只提出，不实现）：**加一层"熔断"逻辑**——第一次收到 429 后，与其继续按 0.33/s 排队傻等（反正大概率还在冷却期内，等到的令牌大概率还是换来一个 429），不如直接短路：接下来 5~6 分钟内的 academic 域查询主动跳过 arXiv（只用 CrossRef），省下这段时间里注定失败的请求所占用的排队等待时间，缩短受影响的子问题拿到回复的时间。这不会减少"被限速的次数"，但能减少"确定会失败的等待成本"。是否要做，留待决策。

结果已保存（未入库），脚本产出直接打印在后台任务日志里，未生成 `benchmark/results/` 标准结果文件。

### 9.26 实现熔断并跑 12 题基准验证：arXiv 失败数从 67 降到 6，但 CrossRef 出现新的零星失败

承接 §9.25 提出但没做的熔断思路，本节把它落地并用真实基准验证效果。参数本身不动——§9.25 两组独立实验已经证明现有 `arxiv_rate_limit_per_sec=0.33`、`burst=1`、`arxiv_max_concurrency=2` 是安全组合，不需要往更保守调，本节只加熔断逻辑。

**实现**：`academic_api.py` 新增模块级状态 `_arxiv_circuit_open_until`（进程内本地状态，不追求跨 worker 共享）。`_query_arxiv()` 入口先检查是否处于熔断窗口内，是则直接返回 `None`、不发起真实 HTTP 请求；`httpx.HTTPStatusError` 分支里专门捕获 429，把 `_arxiv_circuit_open_until` 设为当前时间 + `arxiv_circuit_breaker_cooldown`（新增配置项，360s——比 §9.21/§9.24 实测的约 298s 冷却期留了余量）。`search_arxiv()` 原有的"精确匹配→宽松匹配"两级重试逻辑不用改，`_query_arxiv()` 返回 `None` 时会自然短路掉两次调用。落地前用 `verify_circuit_breaker_unit.py` 做了 mock 单测，验证熔断触发、熔断期内跳过（不发真实请求）、窗口过期后恢复正常尝试三段行为均符合预期；`pytest`（33/33）和 `ruff check` 均无回归。

**真实 12 题基准结果**（`benchmark/retriever_benchmark.py -c 2`，与 §9.24/§9.25 同规模）：

| 指标 | §9.24（干净起点，未加熔断） | §9.26（加熔断后） |
|---|---|---|
| arXiv 429 次数 | 67 次，散布在运行的大部分时间段 | **6 次**，全部集中在同一小段（日志第 175~180 行，约 6 个并发中的请求几乎同时撞线） |
| CrossRef 429 次数 | 0 次 | 6 次，分散在 6 个不同任务里 |
| 总耗时 | 616.1s | **540.4s**（-12.4%） |
| 任务正确性 | 12/12 全覆盖 | 12/12 全覆盖 |

**arXiv 侧效果符合预期**：本轮只撞进一次真实冷却状态——6 个几乎同时在飞的请求各自独立命中 429、各自设置了一次熔断窗口（内容重复，属预期内的无害重复写入），此后整个 1242 行日志里再没出现过一次 arXiv 429。熔断期内的跳过日志是 `logger.debug` 级别，当前基准脚本的日志配置在这个级别下不输出，所以看不到具体跳过了多少次，但从"此后总耗时收窄、且没有再产生新的 429"这两点可以确认熔断在真实起作用——省下的是这些注定失败的请求本该占用的排队等待时间。

**如实记录一个没预期到的现象**：CrossRef 这次出现了 6 次 429，是 §9.22 接上令牌桶之后第一次在完整基准里观察到 CrossRef 失败（此前 §9.23/§9.24 两轮都是 0 次）。CrossRef 侧本节完全没有改动代码，这 6 次分散在 6 个不同任务、不同子问题的查询里，不是同一小段时间内的突发，更像是这次跑基准时 CrossRef 服务端本身的负载波动，而不是我们客户端行为的变化——但样本量只有一次运行，不足以下"CrossRef 限速开始不稳定"这种结论，只如实记录，后续如果重复出现再深挖。

**结论**：熔断没有降低 arXiv"被判定进入冷却状态"这件事发生的概率（这本来就不是熔断能解决的，§9.25 已经确认这部分不完全受客户端控制），但确认了它能把"一旦触发，就别再拿后续请求去送死"这件事落到实处——67 次失败降到 6 次、总耗时进一步收窄 12.4%，是三轮里目前耗时最短的一次。至此 arXiv 相关的这一轮优化告一段落：客户端能做的（避免主动制造突发、命中冷却后及时止损）都已经做了，剩下不受控的部分（是否进入冷却状态本身）留给后续如果需要再考虑申请官方 API key 之类的更高层手段。
